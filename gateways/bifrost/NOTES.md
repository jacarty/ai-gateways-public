# Bifrost: how it works

Phase 2 notes on Bifrost (OSS, Apache 2.0), gateway release **`transports/v2.2.6`** (released 2026-10-06, commit `8b4fce4`), image `ghcr.io/maximhq/bifrost:v2.2.6` = `sha256:d0b4708a…` (multi-arch index; the same digest on Docker Hub), pulled through `agw-ghcr` and deployed by digest. Findings below are from reading the source at that tag unless marked *to test*.

**Release choice:** the repo tags each Go module separately (`core/`, `framework/`, `plugins/*`, `transports/`); `transports/vX` is the gateway binary and the image tag. v2.2.6 is the newest at least two weeks old on 2026-10-22; v2.3.0 (2026-10-13) and later are too new. `ent-v*-base` tags are the enterprise build's base and are not used.

## What it is

One Go binary (`transports/bifrost-http`, on `fasthttp`) that exposes an OpenAI-compatible API (`/v1/chat/completions`, plus Anthropic-, Gemini- and other provider-shaped routes under integration prefixes) and translates each request to the provider's native API. The Go packages under it are also usable as an SDK (`core/`), which this lab doesn't use.

The image is a **monolith** like LiteLLM's: API, admin UI (a React app built into the binary) and the config/log stores (SQLite by default) in one container. It runs as UID 1000 with `APP_DIR=/app/data` (config file, SQLite databases, logs).

## Request path

1. **Transport middlewares.** Optional dashboard/API auth (below), then the plugins' `HTTPTransportPreAuthHook` / `HTTPTransportPreHook`. Credentials are read from headers: a **virtual key** is the value of `x-bf-vk` (any value), or an `sk-bf-…` value in `Authorization: Bearer`, `x-api-key`, `x-goog-api-key` or `api-key`; a non-`sk-bf-` value in those headers is a *direct provider key*, honoured only with `allow_direct_keys` and an `x-bf-direct-key: true` header. Caller headers are not forwarded upstream unless an allowlist says so (`lib/ctx.go`). On Cloud Run the ID token sits in `X-Serverless-Authorization`, which Cloud Run checks and Bifrost doesn't read, so `Authorization: Bearer sk-bf-…` reaches Bifrost as the virtual key: the harness's existing header layout should work unchanged (*to test*).
2. **Built-in plugins, in order** (`server/plugins.go`): prompts, logging, governance (virtual keys, budgets, rate limits), routing rules, OTel, semantic cache, compat, Maxim, then the model-catalog resolver last.
3. **Provider resolution.** A model written `vertex/<model>` names its provider. A bare model (`gemini-3.8-flash`, what the harness and agent send) has no provider, and the last routing layer fills it in: the virtual key's provider configs, a routing rule, or the model catalog (`modelcatalogresolver`). With one provider configured, bare names should resolve to `vertex` (*to test*; otherwise callers would need a `vertex/` prefix, which would change the agent's and harness's model setting).
4. **Translation** (`core/providers/vertex`). Gemini goes to `generateContent` / `streamGenerateContent`; Claude (`IsAnthropicModelFamily`) to Anthropic Messages on `publishers/anthropic/…:rawPredict` / `:streamRawPredict`, the same native paths as the direct baseline. Auth to the Agent Platform: when the key's `auth_credentials` is empty, `google.FindDefaultCredentials`, so on Cloud Run the gateway's service account `agw-gw-bifrost`, with no keys (workload identity).
5. **Region.** `region: eu` maps to `aiplatform.eu.rep.googleapis.com` (`getVertexAPIHost`), the baseline's endpoint. Bifrost also **promotes** a single region (`europe-*`) to the `eu` pool for models its datasheet marks multi-region-only, unless `force_single_region`; with `eu` set directly there is nothing to promote. Model *listing* uses `aiplatform.googleapis.com` (the pool hosts reject list calls).
6. **Response.** Translated back to OpenAI shape; cost comes from the model catalog's prices (below); logging and telemetry plugins run after the response.

**Retries are off by default** (`DefaultMaxRetries = 0`; backoff 0.5-5 s when set), so unlike LiteLLM no setting is needed to keep upstream errors visible. Default provider request timeout 300 s.

**Thinking.** For Gemini 3, `reasoning_effort` becomes `thinkingLevel` **with `includeThoughts: true`** (the same quirk as LiteLLM; the direct baseline sends no thought summaries). `gemini-3.8-flash` is not in Bifrost's per-model level table (newest entry `gemini-3.7-flash`), so it gets the Gemini 3 default rungs `low/medium/high`: `"low"` passes through. Callers send `reasoning_effort` to Gemini only (the harness and the agent; Claude's condition is thinking off), so Claude requests carry no reasoning parameter and Bifrost adds no thinking; sent to Claude, it would turn adaptive thinking on (Findings).

## Config model

- **`config.json`** in `APP_DIR` (schema: `transports/config.schema.json`): `providers` (keys per provider; for Vertex `vertex_key_config` with `project_id`, `region`, `auth_credentials`), `governance` (virtual keys, budgets, rate limits, customers, teams, routing rules, `pricing_overrides`), `client` (logging, header handling, `enforce_auth_on_inference`, `allow_direct_keys`, `disable_content_logging`), `plugins`, `config_store`, `logs_store`, `framework.pricing`. Values written `env.NAME` are read from the environment.
- **Config store** (SQLite or Postgres) holds what the UI and API change. `source_of_truth` decides how the file and the store reconcile: `split` (the default, merge) or `config.json` (sections present in the file win at startup). The file is the codified baseline here, so `config.json` is the likely choice (*to decide* in codify).
- **Logs store** (SQLite, Postgres or ClickHouse): per-request logs for the UI. **Content is logged by default** (`disable_content_logging: false`); request headers are logged only if listed in `logging_headers` (opt-in, unlike LiteLLM's `store_prompts_in_spend_logs`, which stored the ID token), plus any `x-bf-lh-*` header a caller chooses to send, which lands in the log's metadata (`plugins/logging/main.go`): a caller-controlled path into the logs. Test 6 checks both.
- **Encryption key** (`encryption_key` / `BIFROST_ENCRYPTION_KEY`) encrypts stored credentials; without one they are stored in plain text, and it can't be changed without clearing the database.
- **Admin access.** In OSS, while no admin account exists every `/api` call needs `X-Bifrost-Setup-Token` (`setup_token` / `BIFROST_SETUP_TOKEN`); `governance.auth_config` sets an admin username and password for the dashboard and API. `enforce_auth_on_inference` makes inference require a virtual key.

**Prices come from the network.** The model catalog downloads `https://getbifrost.ai/datasheet` at startup and on a timer (`framework.pricing.pricing_url` and `pricing_sync_interval` override it). It is a live file, not part of the release, so a price can change between two runs of the same image. On 2026-10-22 it has:

| Model | Datasheet input / output per 1M | Datasheet uplift field | Real (EU multi-region) |
|-------|------|-----|------|
| `vertex_ai/gemini-3.8-flash` | $0.75 / $3.75 | ×1.1 | $1.65 / $8.25 (Cloud Billing catalogue) |
| `vertex_ai/claude-haiku-5-5` | $0.10 / $0.50 | ×1.1 | $0.11 / $0.55 (Agent Platform pricing page) |

Gemini is at **half** price, the same error as LiteLLM v1.103.2's map (the datasheet carries LiteLLM-derived fields in places). And Bifrost v2.2.6 **never applies the uplift**: no Go code reads `regional_endpoint_uplift_multiplier`, so it would charge the global prices, Gemini at 45% of its real EU price and Haiku at $0.10 / $0.50. As in Phase 1 (ADR 0009), `config.json` sets both EU prices explicitly (`governance.pricing_overrides`, provider scope, exact model match, `chat_completion`, which covers streaming too), and test 3 checks the computed cost against tokens × price.

## Extension model

- **Plugins** implement Go interfaces (`core/schemas/plugin.go`): `HTTPTransportPreAuthHook` (before auth; "deriving a virtual key from an upstream identity header" is its documented use), `HTTPTransportPreHook`/`PostHook`, `PreRequestHook` (choose provider, model and fallbacks), `PreLLMHook` (can short-circuit with a response or error) and `PostLLMHook`, plus MCP hooks (out of scope).
- **Built-in plugins** in the OSS repo: governance, logging, routing, semantic cache, OTel, telemetry (Prometheus), mocker (canned responses and errors, for test 2), JSON parser, prompts, compat, Maxim (the vendor's observability SaaS), model-catalog resolver.
- **Custom plugins** are Go shared objects (`.so`) loaded by path from `plugins`, built against the exact Bifrost version. **The published image can't load them:** it is statically linked (`-extldflags '-static'` in `transports/Dockerfile`), and Go plugins need a dynamically linked binary (`docs/plugins/building-dynamic-binary.mdx`). So on OSS a custom plugin means rebuilding Bifrost itself, not just the plugin, as a custom image (with `scripts/build-image.sh`). WASM plugins existed and are deprecated. No plugin marketplace.
- A pre-auth plugin could map the caller's Cloud Run identity (the `X-Serverless-Authorization` ID token, already verified by Cloud Run) to a virtual key: an OSS route to binding the gateway principal to the caller's identity, which LiteLLM gated (JWT auth). Test 5 decides whether that is worth building; it would be custom code and a custom Bifrost build, not a Bifrost feature.

## OSS vs enterprise

`LICENSE`: Apache 2.0 for the whole repository. Unlike LiteLLM there is **no enterprise code in the OSS image and no licence key**: the enterprise edition is a separate, closed build layered on the OSS code through seams in the transport (hooks for clustering, vault, large payloads, the load balancer, a custom logo), and its UI pages replace stubs under `ui/app/_fallbacks/enterprise/`. In the OSS image each enterprise page is a "contact us" view, and four enterprise log exporters are skipped silently if configured (`enterprisePlugins`: datadog, bigquery, pubsub, kafka). So the OSS ceiling here shows as a feature that is absent, not one that fails at runtime (to confirm per test: LiteLLM's gates failed four different ways).

Enterprise-only in v2.2.6, from the fallback pages and the transport source:

| Area | Enterprise-only | Matters for test |
|------|-----------------|------------------|
| Routing | Adaptive routing, the enterprise load balancer, circuit breaker | 2 |
| Cost | Projects (scoped access and spend), access profiles, user-level governance and rankings, scoped API keys | 3 |
| Guardrails | All guardrails (content policy, PII, injection) | 4 |
| Identity | SSO login, RBAC (roles and permissions), SCIM, user groups, vault/secret-manager integration, scheduled key rotation | 5 |
| Logging | Audit logs, alerting, log export to BigQuery / Pub/Sub / Kafka / Datadog | 6 |
| Other | Cluster mode, large-payload optimisation, prompt deployments, custom branding, MCP auth and virtual MCPs | — |

OSS in the same build: virtual keys with budgets and rate limits (governance plugin), fallbacks (`fallbacks` on the request), routing rules, manual virtual-key rotation (`POST /api/governance/virtual-keys/{id}/rotate`, with a cooldown), semantic cache, OTel and Prometheus, logs store and UI, custom `.so` plugins (with a dynamically linked build of your own), the mocker.

**Day-1 split** (`docs/day1-checks.md`): right. Routing, fallbacks, virtual keys, budgets, caching, OpenTelemetry and custom plugins are OSS; guardrails, adaptive load balancing, clustering, secret manager, audit logs and SSO/RBAC are enterprise. The source adds circuit breaker, alerting, projects, log exporters and SCIM to the enterprise side, and manual key rotation to the OSS side (LiteLLM gated rotation). Test 4 therefore has no built-in screening to test on OSS: the gap is the finding, unless a custom plugin is written (out of the vendor's feature set, so not counted as Bifrost's).

## How it is deployed here

`gateways/bifrost/terraform` (state prefix `gateways/bifrost`, exact pins), with the LiteLLM stack's guardrails:

- **Cloud Run** `agw-bifrost`, `europe-west1`, min 0, max 1, as `agw-gw-bifrost`; 1 vCPU and 2 GiB with CPU always allocated (the same as LiteLLM); image by digest through `agw-ghcr` (validated); invoker-only IAM (validation rejects `allUsers`). Startup probe on `/health` (exempt from auth) with about two minutes.
- **Config:** [config/config.json](config/config.json) from a Secret Manager secret (`agw-bifrost-config`, version pinned), mounted outside `APP_DIR` and copied in at start, because Cloud Run secret volumes are read-only (the pattern Bifrost's own Cloud Run module uses). `source_of_truth: config.json`. One Vertex key (ADC, `region: eu`); one virtual key per caller (`agw-agent`, `agw-harness`) with both models allowed and no budgets or limits; explicit prices; dashboard login for `admin` (`governance.auth_config`), which also closes `/api` to anyone without a session or the admin password (HTTP Basic works too). Virtual keys are refused on `/api`, with one exception: `GET /api/governance/virtual-keys/quota` answers a caller's own key with its budgets, limits and usage (read-only).
- **Secrets** (`agw-bifrost-*`), all generated by Terraform: admin password, setup token (backstop), encryption key, database password, and the two virtual-key values (`sk-bf-…`; each caller's service account reads only its own). Unlike LiteLLM's, no key is minted by hand after a deploy.
- **State: Cloud SQL Postgres for both stores (decided 2026-10-22).** `APP_DIR` on Cloud Run is the instance's in-memory filesystem, so SQLite stores would vanish on scale-to-zero, taking budget usage (test 3) and request logs (test 6) with them. Bifrost's own Cloud Run guide (`docs/deployment-guides/platforms/cloud-run.mdx`) says the same, marks Cloud Run with one Postgres-backed instance as "Preview", and says to keep OSS at `max-instances=1`. Bifrost refuses to start on PostgreSQL older than 16; Phase 1's instance shape (`db-f1-micro`, Postgres 16, Cloud SQL socket, no VPC) carries over, with `make stop-bifrost` / `make start-bifrost` between sessions. Governance state is cached in memory (the governance plugin also runs with no store at all), so the database is off the request's hot path; when request logs are written relative to the response is *to test*.
- **Database connection:** both stores' `host` is the Cloud SQL socket directory (`/cloudsql/<connection name>`), which pgx takes as a Unix socket; `ssl_mode: disable` (the connector encrypts the link); 4 connections per pool, two pools, so 8 of `db-f1-micro`'s ~25: a revision change briefly runs two instances, and both must fit.
- **Not used:** Bifrost's Terraform module (`terraform/modules/bifrost/gcp`): it grants `allUsers` invoker, gives the service account project-level `secretAccessor`, and builds a VPC and firewall for the GKE variant.

## Findings so far

- **Test 7, OSS ceiling (2026-10-24):** every test's core ran on OSS except screening, which has nothing. Enterprise adds guardrails, adaptive routing and circuit breaker, projects and user-level governance, SSO/RBAC/SCIM, the audit log and log exporters. The ceiling shows quietly: configured enterprise features are ignored (`guardrails_config`, the export plugins), enterprise API routes return the UI page with HTTP 200, and the UI shows "contact us". Narrower than LiteLLM's in governance (per-model budgets and rotation are OSS here), wider in screening. Details: `results/summary.md`.
- **Test 6, audit fidelity (2026-10-24, `results/raw/bifrost/*audit*`):** one log row per request that reached a provider (key, model, provider key, tokens, cost, latency, session, the caller's own `x-bf-lh-*` tags, content), and the `x-request-id` Bifrost returns is the row's id, so a caller can quote it. Governance refusals (403, 429) leave a row; a 400 at provider resolution leaves none. The agent hop joins only by key and time; no log names a Google identity. Content is stored by default (365 days) but no headers; `logging_headers` makes every row keep callers' ID tokens and virtual keys (run B). Admin audit log: enterprise. Details: `results/summary.md`.
- **Test 5, identity and secrets (2026-10-24, `results/raw/bifrost/20261024T135211Z-scenarios-bifrost-auth-2d6094`):** gateway → model is workload identity only (no SA keys; org policy blocks them). Caller → gateway is Cloud Run IAM (HTML refusals) then the virtual key alone (JSON), a bearer secret: the agent's key works from any invoker. Key states are OSS and immediate, rotation included (enterprise in LiteLLM); unknown, deleted and rotated-away keys are indistinguishable, and no refusal echoes a key. A Claude-only key asking for Gemini by bare name gets a misleading 400 (provider resolution) rather than the 403 an explicit `vertex/` name gets. `x-bf-vk` accepts any value. All gateway secrets are in Secret Manager. Details: `results/summary.md`.
- **Test 4, inline screening (2026-10-24, `results/raw/bifrost/*screening*`):** no screening at all on OSS: every PII value leaked, injections reached the model (which refused them, as through LiteLLM). A `guardrails_config` (Bifrost's documented regex example) was accepted and silently ignored: no OSS code reads it, no log line, identical results. Content is logged by default in Postgres (prompt and answer, 365-day retention), without ID tokens or keys. Bifrost's own `overhead_latency` per request: median 1.9 ms. Details: `results/summary.md`.
- **Test 3, cost control (2026-10-24, `results/raw/bifrost/*cost-*`):** every limit hard, OSS, refused before the model call (429 rate, 402 budget, ~13 ms). No reservation: the crossing request is admitted, and a burst is admitted while usage is under the limit (10 requests spent 3.1× a budget of 3), the opposite of LiteLLM's worst-case reservation. Per-model budgets work on OSS (enterprise in LiteLLM). Charges match tokens × the EU override price exactly. An alias is priced as the model it resolves to, so it can't make an unpriced model. The self-service quota endpoint lags the enforced counters. A restart removes admin-API keys (confirmed). Details: `results/summary.md`.
- **Empty config sections clear the database (2026-10-24).** `source_of_truth: config.json` resets every section the file declares at start, including an empty one: with `"routing_rules": []` in the file, a window's rule was removed by the next deploy (revisions `00008`-`00010`). The committed file declares `routing_rules`, `budgets` and `rate_limits` empty, so closing a window in those sections is one step. The flip side: `virtual_keys` is declared, so a restart removes keys made through the admin API (confirmed in test 3).
- **Test 2, failover (2026-10-24, `results/raw/bifrost/20261024T092947Z-scenarios-bifrost-failover-318543`):** works both ways and streaming, on real upstream 404s; the caller is told (`model` plus `extra_fields.routing_info.is_fallback`). Fallbacks come from routing rules (operator) or the request's own `fallbacks` list (any caller, no config); a rule's fallbacks override the caller's, and the caller can't opt out. A fallback keeps the original parameters: Claude → Gemini thinks at Gemini's default (137 reasoning tokens in the notebook's saved check, 174 of the 256 cap). When every fallback fails, the caller gets the primary's error. No way to force an error on a healthy model (the mocker isn't in the gateway build). Closing a window with `git checkout` + deploy left its routing rules active in Postgres (twice): sections the committed file lacks are documented to be left alone, so check any a window adds. Details: `results/summary.md`.
- **Test 1, overhead (2026-10-24, `results/raw/bifrost/20261024T070044Z-compare-666edc`):** not distinguishable from zero. Claude p50 −69 to +58 ms and TTFT p50 +20 to +75 ms against direct at concurrency 1 and 5, Gemini inside its own drift, 1,600/1,600 answered. The gateway path was faster in six of eight cells: read as zero (one untested hypothesis: the harness's direct requests send `x-goog-user-project`). No rise with concurrency, unlike LiteLLM's single uvicorn worker. On the agent path Bifrost's share is between nothing and about 70 ms, a rough cross-job estimate at 20 requests a cell. Claude's tokens matched direct: no thinking added. Details: `results/summary.md`.
- **Codified stack up (2026-10-22).** The first apply failed its startup probe: Bifrost hung at "connecting to postgres database" with no error, because `roles/cloudsql.client` is granted in the same apply that creates the first revision (a race first seen in Phase 1); a second apply replaced the service and it started. The stack now waits 60 s after the grant (`time_sleep`). First start on Postgres: 18 s of migrations on `db-f1-micro`, then the catalog download. The smoke calls and both agent apps passed again with each caller's own key; the admin API then answers 401 "Unauthorized" (admin account active).
- **Requests during a rollout can get Cloud Run's 429.** With `max_instances = 1`, the first request after `agw-bifrost-00002` rolled out got HTTP 429 "no available instance" from Cloud Run (not Bifrost), and the next took 15 s; a moment later both were normal. The same cap applied to LiteLLM. Never deploy during a measured run; `compare`'s prewarm absorbs the first slow request.
- **Hand-build passed (2026-10-22).** A manual `gcloud run deploy` of the digest (`agw-bifrost-hand`, temporary, SQLite in memory, no database) answered Gemini and Claude, streaming and not, through the harness's request shape: bare model names (resolved to `vertex`), `max_completion_tokens`, `reasoning_effort: "low"`, `stream_options.include_usage` (streams end with a usage chunk, then `[DONE]`). Then the agent (`AGW_TARGET=gateway`, `gateway_url = <url>/v1`) answered through it on both apps. Layers refuse as expected: no credentials → Cloud Run's HTML 403; an ID token with no virtual key → Bifrost's JSON 401 `virtual_key_required`; the admin API without the setup token → 401.
- **Cold start ~28 s, most of it the network.** Migrations of the (empty) SQLite store take under a second; the model catalog's download of 13,257 parameter records from `getbifrost.ai` took 22 s. Every cold start depends on that site.
- **A caller that sends `reasoning_effort` to Claude gets thinking switched on.** For `reasoning_effort: "low"`, Bifrost sends Claude `thinking: {type: "adaptive"}` plus `output_config.effort: "low"` (`core/providers/anthropic/chat.go`), because the datasheet marks `vertex_ai/claude-haiku-5-5` `supports_adaptive_thinking` and `supports_native_effort`: a capability chosen by a live file. The harness and the agent send `reasoning_effort` to Gemini only (Claude's test condition is thinking off), so measured runs are unaffected: with no reasoning parameter Bifrost adds no thinking. The smoke script sent it to both, which is how this showed.
- **Gemini thinking through the agent varies.** One agent → Bifrost → Gemini call reported 79 thought tokens (4.3 s at the gateway), the next (after the codified deploy) none; the harness-shaped curls none. Test 1 counted one Gemini request in 100 thinking on each path (`results/summary.md`).
- **Responses carry `extra_fields`:** routing info (provider, model, key name), latency, and Vertex's own response headers (`provider_response_headers`). Gemini messages also carry `reasoning_details` with an encrypted thought signature. Harmless for the harness (it reads `choices` and `usage`), but they tell a caller which key and upstream answered: noted for tests 5 and 6.
- **Gemini's thinking count is missing, not zero**, as through LiteLLM: `completion_tokens_details` has no `reasoning_tokens` when Gemini doesn't think.
- **Source check (2026-10-22):** the Vertex provider supports the `eu` multi-region host and ADC (workload identity) out of the box, and calls Claude through `rawPredict`, the baseline's path. Retries default to 0. Prices for Gemini 3.8 Flash are half the real figure in the live datasheet.

## Confounds

- **Sizing:** one instance (max 1, for in-memory rate-limit counters without a cluster) with the same CPU and memory as LiteLLM's, so test 1 compares the gateways, not their sizing. Go uses every vCPU it is given (`automaxprocs`); LiteLLM ran one uvicorn worker.
- **Live prices:** the datasheet can change under a fixed image; explicit prices in the config remove that.
- The agent's gateway mode uses LiteLLM as its client library (ADK's `LiteLlm`) for every gateway; overhead numbers come from the harness → gateway path.

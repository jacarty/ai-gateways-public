# Kong OSS: how it works

Phase 3 notes on Kong Gateway OSS (Apache 2.0), release **`3.9.3`** (released 2026-06-17, commit `a643428`), image `kong/kong:3.9.3` = `sha256:9a2ae6699a2ce0d60592eb176555d3594a22782c20cc6557a61ff3a7e8b559a3` (multi-arch index, amd64 + arm64; unchanged since release), pulled through `agw-dockerhub` and deployed by digest. Findings below are from reading the source at that tag unless marked *to test*.

**Release and image choice:** OSS Kong is still on the 3.9 line (no OSS 3.10+). 3.9.4 (2026-10-12) is too new, and its `kong/llm` and `kong/plugins/ai-*` are identical to 3.9.3's. Three images carry the name: `kong/kong` (OSS, built by Kong's release pipeline), `library/kong` (the Docker Official Image, also OSS, but rebuilt for base-image fixes, so its 3.9.3 digest moves; last rebuilt 2026-10-02) and `kong/kong-gateway` (**Enterprise**, which runs in free mode without a licence: not used). `kong/kong` gives one stable digest built from the tag read here.

## What it is

A general API gateway (OpenResty: nginx + LuaJIT) whose behaviour comes from **plugins** attached to **routes**, **services** and **consumers**. AI support is a set of plugins, not a separate product: `ai-proxy` turns a route into an LLM endpoint and translates an OpenAI-format request to one provider's API. Everything else (auth, rate limits, logging) is the ordinary API-gateway plugin set, which knows nothing about tokens or models.

The image is one process tree: an nginx master and `nginx_worker_processes = auto` workers (one per CPU), the proxy on 8000, the Admin API on `127.0.0.1:8001`, the status API on `127.0.0.1:8007`, and the Kong Manager OSS UI (v3.9.0.0, bundled) on 8002. It runs as user `kong`, `CMD kong docker-start`, `STOPSIGNAL SIGQUIT`. Here: one worker, the proxy on 8080, the status API on 8100 for the startup probe, and Manager on loopback under `/manager` (How it is deployed here).

## Request path

1. **Router.** A request matches a **route** (by path, host, method or header, never by body), which belongs to a **service** (the upstream). **There's no routing by `model`:** each `ai-proxy` instance is pinned to one model and rejects any other with 400 `cannot use own model - must be: <name>` (`normalize-request.lua`). Two models therefore need two routes, told apart by path. That fits the Claude path below, which already uses a different URL.
2. **Plugins, by fixed priority** (higher first; dynamic ordering is enterprise): `cors` 2000, `key-auth` 1250, `request-size-limiting` 951, `acl` 950, `rate-limiting` 910, `request-transformer` 801, then the AI plugins `ai-request-transformer` 777, `ai-prompt-template` 773, `ai-prompt-decorator` 772, `ai-prompt-guard` 771, `ai-proxy` 770, `ai-response-transformer` 768, and the loggers last (`opentelemetry` 14, `prometheus` 13, `http-log` 12, `file-log` 9).
3. **`ai-proxy` filter chain** (`kong/llm/plugin/shared-filters/`): `parse-request` → `normalize-request` (merge `model.options`, check the model, transform the body with the driver's `to_format`, then `configure_request` sets the upstream URL and auth) → `enable-buffering` → response filters (`normalize-response-header`, `parse-sse-chunk`, `normalize-sse-chunk`, `parse-json-response`, `normalize-json-response`) → `serialize-analytics` (token counts, latency and cost into the log record).
4. **Upstream URL and auth for Vertex.** `provider: gemini` with `model.options.gemini.{api_endpoint, project_id, location_id}` builds `https://<api_endpoint>/v1/projects/<p>/locations/<l>/publishers/google/models/<model>:generateContent` (`shared.lua:151`). The path is fixed to `publishers/google`. With `auth.gcp_use_service_account: true`, Kong gets a token from `lua-resty-gcp` 0.0.13, which **tries the metadata server first** (`GetAccessTokenByWI`), then a service-account JSON. So on Cloud Run Kong calls Vertex as `agw-gw-kong`, with no key. That cloud identity is loaded **only for `provider: gemini`** (and bedrock); every other provider gets only static header, query or body auth.
5. **Response.** In translated mode it is turned back into OpenAI shape. Cost is computed for the log only, from `model.options.input_cost` / `output_cost` (per 1M tokens); with no prices it is absent. **Nothing in OSS enforces it.**

**Headers upstream.** Kong forwards the caller's request headers to the upstream by default. `ai-proxy` overwrites `Authorization` with the GCP token, and `key-auth`'s `hide_credentials` (default **false**; we set it to true) decides whether its key header is stripped. `X-Serverless-Authorization` (the caller's ID token) reaches Kong with its claims but its **signature replaced** by Cloud Run (probed 2026-10-28: a 27-character placeholder), so it is not a usable token if Kong forwards it to Vertex. Test 5's echo window showed it does reach the upstream (claims intact, 27-character signature), with every other caller header (`results/summary.md`). Cloud Run also rejects a forged `X-Serverless-Authorization` itself, even when a valid token sits in `Authorization`.

### Gemini: translated, with two gaps

`to_gemini_generation_config` maps `max_tokens`, `stop`, `temperature`, `top_k` and `top_p`, nothing else:

- **`max_completion_tokens` is dropped**, and it is what the agent and the harness send: Gemini through Kong would have no output cap. `model.options.max_tokens` in the config forces one (`merge_config_defaults` overrides the request), so the config pins 256.
- **`reasoning_effort` is dropped, and there is no `thinkingConfig` mapping at all.** Gemini thinks at its default level, not the baseline's `LOW`, and **the config can't fix it.** That's a comparability finding for test 1 (and a spend one, since thinking tokens are billed).
- Token counts use `candidatesTokenCount`, which **excludes thinking tokens**, so Kong's logged completion tokens and cost under-count Gemini.

### Claude: no translated path, so `preserve` (decision 2026-10-24, option A)

- **The `gemini` provider can't reach Claude:** its Vertex path is fixed to `publishers/google`.
- **The `anthropic` provider speaks api.anthropic.com's dialect.** It puts `model` in the body and `anthropic-version` in a header, where Vertex wants `anthropic_version` in the body, and it gets no GCP identity (static auth only, and an access token expires within an hour).
- **Vertex's OpenAI-compatible endpoint doesn't serve Claude in `eu`.** Probe on 2026-10-24: `anthropic/claude-haiku-5-5` gave 400 "not servable in region eu", while `google/gemini-3.8-flash` gave 200.
- **What works:** a **`provider: gemini` route with `route_type: preserve` and `model.options.upstream_url` set to Claude's `…/publishers/anthropic/models/claude-haiku-5-5:rawPredict`**, plus a second route for `:streamRawPredict`. With `upstream_url` set, the driver uses it as is, and still adds the GCP token (`gemini.lua:641`, `:703`). `preserve` skips the body transform, so the caller's native Anthropic body reaches Vertex unchanged.
- **Callers change for Kong.** The agent's direct Claude client (`AsyncAnthropicVertex`) gets `base_url` pointed at Kong, plus the ID token and the Kong key. The harness reuses its `direct` rawPredict request against the gateway. Both are switched by environment, not by code changes per run. The Anthropic SDK's Vertex client sends `Authorization: Bearer <access_token>` and skips Google auth when `access_token` is given (`anthropic/lib/vertex/_client.py`), so passing the Kong key as `access_token` gives exactly the header `key-auth` checks; the ID token goes in `X-Serverless-Authorization`, refreshed per request as the gateway client already does (confirmed in the hand-build, 2026-10-25).
- **What `preserve` gives up:** Kong does no translation, records no token statistics or cost for Claude (`normalize-json-response` returns early in `preserve_mode`), and `ai-prompt-guard` only reads string `content`, while native Claude messages use content blocks (*to test*, test 4). So Claude through Kong is an authenticated proxy, not an AI-aware one: that is the test 7 finding.

## Config model (Postgres + decK)

Kong runs on Postgres here (ADR 0015), so the lab can later run all three gateways side by side in the same shape.

- **Two modes.** With `KONG_DATABASE=postgres` the entities (services, routes, plugins, consumers, credentials) live in the database and the Admin API creates, updates and deletes them at runtime; Kong caches them in memory and polls for changes. With `KONG_DATABASE=off` (DB-less) a **declarative config** (`_format_version: "3.0"`, from `KONG_DECLARATIVE_CONFIG` or `KONG_DECLARATIVE_CONFIG_STRING`) is the whole config, and the Admin API is read-only except `GET /config` / `POST /config` (replace everything, until the next restart).
- **What a database adds in OSS:** runtime entity writes, a `ttl` on credentials (keys that expire on their own) and the `cluster` rate-limit policy. **What it doesn't:** request logs and rate-limit counters aren't stored in it, and the AI plugins behave the same either way.
- **Schema migrations.** A new database needs `kong migrations bootstrap`; an upgrade needs `kong migrations up` then `finish`. Here a startup wrapper (`config/start.sh`) runs them before `kong docker-start`, choosing the step from `kong migrations list`'s exit code (0 up to date, 3 needs bootstrap, 4 pending, 5 new).
- **The declarative file, with a database.** `kong config db_import <file>` loads a file into the database but only **upserts** (`kong/db/declarative/import.lua:148`): an entity removed from the file stays live, Bifrost's undeclared-section trap again. So **decK** (`deck gateway sync`), Kong's own declarative tool, is the source of truth: it diffs `config/kong.yaml` against the Admin API and deletes what the file doesn't declare, within a select tag. Its `${{ env "DECK_…" }}` substitution keeps key values out of the committed file.
- **The Admin API** listens on `127.0.0.1:8001` only. decK, the live-config check and the test scripts reach it through a Kong route (`/admin-api` → the loopback service), behind Cloud Run IAM, `key-auth` and `acl` (group `admin`). The startup wrapper `db_import`s a small bootstrap file with just those entities (fixed IDs, so each start is an upsert); `kong.yaml` declares the same ones, so a sync keeps them.
- **Secrets in the config.** The only OSS vault is `env` (`{vault://env/NAME}`), and only `referenceable` fields can use it: `ai-proxy`'s auth values can, **`keyauth_credentials.key` can't**. Keys are therefore written into the database by decK (from env vars at sync time) or by the Admin API, never committed.
- **Consumers and keys.** `key-auth` looks up `key_names` (default `apikey`) in headers, query or body, and compares the **whole value**: it doesn't strip `Bearer `. Our callers send `Authorization: Bearer <key>` (the OpenAI client), so we use `key_names: [authorization]` with each credential stored as the literal string `Bearer <key>` (decided 2026-10-25, below; the alternative was a separate key header, an agent and harness change). Throwaway keys get a `ttl`.

## Plugin model

- **Bundled OSS plugins (3.9.3):** auth (`key-auth`, `basic-auth`, `jwt`, `hmac-auth`, `oauth2`, `ldap-auth`, `session`), traffic (`rate-limiting`, `response-ratelimiting`, `request-size-limiting`, `request-termination`, `proxy-cache`, `ip-restriction`, `bot-detection`, `acl`), transformation (`request-`/`response-transformer`, `correlation-id`), AI (`ai-proxy`, `ai-prompt-guard`, `-decorator`, `-template`, `ai-request-`/`ai-response-transformer`), logging (`file-log`, `http-log`, `tcp`/`udp`/`syslog`, `opentelemetry`, `prometheus`, `datadog`, `statsd`, `zipkin`), serverless (`pre-function`, `post-function`).
- **`rate-limiting` counts requests, not tokens.** It limits per consumer, credential, IP, service, header or path, by second through year. Policies are `local`, `redis` or `cluster` (database only; counters in Postgres). We use `local`, which keeps counters in nginx shared memory (`kong_rate_limiting_counters`), shared by all workers of an instance, so with max 1 instance it is exact (*to test*, test 3).
- **`ai-prompt-guard`:** up to 10 allow and 10 deny regexes (500 characters each) over the user messages (or all roles), concatenated; it fails the request on a non-string `content`. No PII detection and no model judge in OSS.
- **`ai-request-`/`ai-response-transformer`** call an LLM to rewrite the request or response, at the cost of an extra model call. The request transformer masked PII on Claude's `preserve` route and broke the translated Gemini route (test 4).
- **`pre-function` / `post-function`** run Lua in a sandbox (`untrusted_lua = sandbox`). That's Kong's custom-code escape hatch, the equivalent of LiteLLM's custom guardrail code. Plugins otherwise are Lua rocks loaded through `plugins = bundled,<name>`.
- **Logging:** `ai-proxy`'s `logging.log_statistics` (tokens, latency, cost) and `logging.log_payloads` (request and response bodies) add fields to the log record, which a log plugin such as `file-log` to `/dev/stdout` writes as one JSON line per request, into Cloud Logging. Nothing is logged unless a log plugin is configured (test 6). The serializer records the request headers and redacts only `Authorization` and `Proxy-Authorization` (`pdk/log.lua:878`), so **`X-Serverless-Authorization` (the caller's ID token) would be logged in clear**; `kong.yaml`'s `file-log` overwrites it with `custom_fields_by_lua`.

## OSS vs enterprise

Absent from the OSS source at 3.9.3, so enterprise-only for us: `ai-proxy-advanced` (load balancing, **failover** and routing across models), `ai-rate-limiting-advanced` (**token limits**), `ai-sanitizer` (PII), `ai-semantic-prompt-guard`, `ai-semantic-cache`, `ai-gcp-model-armor`, `ai-azure-content-safety`, `rate-limiting-advanced`, `openid-connect`, `jwt-signer`, `key-auth-enc`, the non-`env` vaults (GCP Secret Manager among them), dynamic plugin ordering, RBAC and workspaces. That matches `docs/day1-checks.md`'s first pass. Expected test 7 hot spots: **test 2** (no failover or model routing at all: one model per route), **test 3** (request counts only, no budget) and **test 4** (regex only). Confirmed in test 7 (2026-11-01, `…192701Z-oss-ceiling-probe`) for the ten plugins it probed (all of the above but `ai-azure-content-safety`): each fails validation on the running gateway with 400 `plugin '<name>' not enabled; add it to the 'plugins' configuration property` (misleading: there is no code to enable), the GCP vault with `vault 'gcp' is not installed`, and `/audit/*`, `/rbac/*`, `/workspaces` and `/licenses` are 404.

## How it is deployed here

`gateways/kong/terraform`, in Bifrost's shape (deploy, sync and calls: `README.md`).

- **Cloud SQL Postgres 16** (`agw-kong-<suffix>`, `db-f1-micro`, zonal, no backups), database and user `kong`, **private IP only** on foundation's `agw-vpc` (ADR 0016). Kong connects over TCP (`KONG_PG_HOST=<private IP>`, `pg_ssl` on) through Direct VPC egress (`PRIVATE_RANGES_ONLY`). The built-in `/cloudsql` socket doesn't work for Kong: the first hand-build (2026-10-25) ran all 67 migrations and the admin import over it, then Kong failed in nginx's `init` phase (`failed to retrieve PostgreSQL server_version_num: host or service not provided`), because there the connector uses LuaSocket (`connector.lua:193`), which can't open `unix:` paths. `make start-`/`stop-kong` work as for the others.
- **Secrets** (`agw-kong-*`), generated by Terraform: the database password, the admin key, the agent and harness keys (each caller's service account reads only its own) and the Kong Manager password. Also as secrets, for mounting as files: the startup wrapper, the admin bootstrap and the database's CA certificate.
- **Cloud Run service `agw-kong`:** IAM-authenticated, max 1 instance, min 0, image by digest through `agw-dockerhub`, service account `agw-gw-kong`. The container command is the startup wrapper (migrations, admin bootstrap import, then the image's entrypoint).
- **Environment:** `KONG_DATABASE=postgres`, `KONG_PG_SSL` and `KONG_PG_SSL_VERIFY` on (the instance's CA plus the system CAs in `KONG_LUA_SSL_TRUSTED_CERTIFICATE`), `KONG_PROXY_LISTEN=0.0.0.0:8080`, one nginx worker, the Admin API on `127.0.0.1:8001`, Kong Manager on `127.0.0.1:8002` (path `/manager`; the API URL setting is overridden by the `kconfig.js` route, see below), the status API on `0.0.0.0:8100` for the startup probe only (Cloud Run routes outside traffic to 8080), logs to stdout and stderr.
- **Config:** `config/kong.yaml`, synced with decK through `/admin-api`.
- **Paths:** `/v1/chat/completions` for Gemini (translated); the rawPredict and streamRawPredict paths for Claude (preserve); `/admin-api` for the Admin API (admin key); `/manager` and `/manager-api` for Kong Manager (`admin` login); `GET /` redirects to `/manager`.

## Findings so far

From source (2026-10-24) unless dated; each one is confirmed or corrected in the hand-build and the tests.

- Kong AI Proxy can't translate to Claude on Vertex; it can only pass a native Claude request through with its own GCP token (above).
- Gemini through Kong loses `max_completion_tokens` (fixable in config) and `reasoning_effort` (not fixable), and its logged completion tokens exclude thinking.
- One model per route, with routing by path or header and never by `model`: no failover between models in OSS.
- `key-auth` doesn't strip `Bearer`, and leaves its key header on the upstream request unless `hide_credentials: true`.
- Cost is log-only, from prices in the config.
- **Credentials are stored and returned in clear** (checked 2026-10-28): `GET /key-auths` returns every key as `Bearer <key>`, because OSS keeps `keyauth_credentials.key` unencrypted (`key-auth-enc` is enterprise). Anyone with the admin key reads every caller's key: a test 5 and test 7 point.

- **Kong Manager (2026-10-28)**, turned on to compare the three gateways' interfaces:
  - **No login of its own, so one was added (test 7 point).** Kong Manager OSS has no authentication (accounts and RBAC are enterprise) and calls the Admin API from the browser, so it can't send `/admin-api`'s key. Here it is served at `/manager` with its API at `/manager-api`, behind Kong's OSS `basic-auth` (user `admin`, `agw-kong-manager-password`), the same login shape as LiteLLM's and Bifrost's UIs (2026-10-28). Cloud Run does verify and forward the caller's ID token (`X-Serverless-Authorization`, signature removed) and rejects a forged one, so an identity check in Kong is possible; it was left out to match the other two. LiteLLM and Bifrost ship a login; on Kong OSS it has to be added by hand. `gcloud run services proxy` passes `Authorization` through untouched, so both basic-auth and the Admin API work behind it.
  - **A login and a key on the same header collide.** On the Manager routes the global `key-auth` is overridden with an anonymous consumer. With `key_names: [authorization]`, its `hide_credentials` stripped the browser's `Authorization: Basic …` before `basic-auth` (priority 1100, after `key-auth` 1250) read it, so the right password got a 401. The override now reads a header nothing sends (2026-10-28).
  - **Kong Manager can't take a relative API URL.** In v3.9.0.0 (`src/config.ts:39`) a relative `admin_gui_api_url` is prefixed with only the protocol (`/manager-api` became `http:///manager-api`), so the browser's list calls never left it and every page but Overview failed (2026-10-28). A host-qualified URL would tie Manager to one host and port, so Kong serves `/manager/kconfig.js` from a `pre-function` with `ADMIN_API_URL = window.location.host + '/manager-api'`.
  - **Redirects must be relative behind the proxy.** Kong's `redirect` plugin takes only an absolute URL, which would send the browser from `localhost` to the `run.app` address and out of the proxy (Cloud Run 403). `GET /` uses a one-line `pre-function` returning a relative `302` instead.
  - **Cross-site access.** With no `admin_gui_url`, Kong's Admin API echoes any `Origin` with credentials allowed (`api_helpers.lua` `cors_filter`). The browser keeps the Basic login for the proxy's origin, so any other site could have read `/manager-api/key-auths` (keys in clear) or posted forms (CSRF). A `pre-function` on both Manager routes refuses `Sec-Fetch-Site` cross-site and non-JSON writes, and drops `Origin` (cross-site read 403, form post 415; Manager unaffected).
  - **decK can't rotate a basic-auth password.** Kong stores a hash, so decK ignores the password: after a rotation the sync was 0/0/0, Kong kept the old password and the secret held a dead one. Deriving the credential id from the password makes a rotation a new credential, but decK creates before it deletes, so the unique username `admin` clashes (409) and decK drops the deletion. `deck.sh` removes the stale credential first.

- **Hand-build, Kong service (2026-10-25)**, temporary `agw-kong-hand` on the Terraform database (private IP `10.20.0.3`, Direct VPC egress), config synced with decK v1.68.0, calls with the harness key and a 256 cap:
  - **Start:** about 5 s; the wrapper skipped migrations (already up to date) and re-imported the admin bootstrap. nginx starts 2 workers on 1 vCPU (the gVisor sandbox reports 2 CPUs).
  - **Gemini, translated:** 200 in 3.3 s, and streaming 200. `usage` was `completion_tokens: 7` with `total_tokens: 254` from a 6-token prompt: about 241 thinking tokens at Gemini's default level (no `reasoning_effort` mapping), which `completion_tokens` leaves out. The stream had **no usage chunk**, although the request asked for one (`stream_options.include_usage`), and its last `finish_reason` was `STOP` (uppercase; non-streaming gave `stop`).
  - **Claude, preserve:** `rawPredict` 200 in 0.65 s and `streamRawPredict` 200, with `x-kong-proxy-latency` 3 ms. Two Kong quirks: **a `preserve` route needs `model.name`**, because the response filter asserts it for the `X-Kong-LLM-Model` header before checking for preserve (`normalize-json-response.lua:88`; without it Vertex's 200 turned into a 502 and the instance restarted), and that header then reads `gemini/claude-haiku-5-5`. Kong also **pads streamed JSON events with spaces**, although `preserve` is meant to pass the body through.
  - **Refusals:** no ID token gave Cloud Run's 403; an ID token with no key gave Kong's 401 `No API key found in request`; another model gave a 400 `cannot use own model - must be: gemini-3.8-flash`; the harness key on `/admin-api` gave a 403 (ACL).
  - **Config changes aren't instant on a database:** a request 0.5 s after a decK sync still saw the old plugin config. Kong reloads changed entities on its cache poll (`db_update_frequency`, 5 s), so test windows wait a few seconds after a sync.
  - **Through the agent** (image `a4802ff`, `AGW_GATEWAY_CLAUDE_API=anthropic`): the `gemini` and `claude` apps both answered (200). Kong logged both as consumer `agent`: Gemini on `gemini-chat` (2716 ms at Vertex, 70 ms in Kong, usage and model in the `ai` log fields; the agent's usage showed about 240 thinking tokens again) and Claude on `claude-raw-predict` (992 ms at Vertex, 3 ms in Kong, no `ai` fields). The first call took 53 s end to end: the new agent revision's and Kong's cold starts.
  - **Terraform service `agw-kong` (2026-10-25):** started in 21 s with `pg_ssl_verify` on (the instance's CA mounted next to the system CAs; Kong checks the chain, not the name, so the private IP verifies). decK's diff against it was empty (same database). All four paths answered. **Gemini's thinking eats the 256 cap:** a plain call used 257 tokens for a 7-token answer, and a stream ended with `finish_reason: MAX_TOKENS` after five words. Gemini counts thinking inside `maxOutputTokens`, and with no `reasoning_effort` mapping it thinks at its default level, so answers can be cut short where the baseline (`LOW`) isn't: a test 1 result, not a harness fault.
  - **Logs:** `file-log` rows show `authorization` and `x-serverless-authorization` as `REDACTED`, with no JWT anywhere in the row; decK's Admin API calls are logged too.

- **Review fixes (2026-10-25):** `key-auth` read keys from the query string by default (`key_in_query`, now off in both config files: `?authorization=` gets a 401); `deck.sh` and `start.sh` no longer put key values in `sed`'s arguments (literal `awk` replacement from the environment), and `deck.sh` also masks any `Bearer <value>` so a diff after a rotation doesn't show the old, still-live key; one nginx worker for the one vCPU. Testing the query-string refusal with the real harness key put that key in Cloud Logging (Kong's `file-log` and Cloud Run's request log record the full URL); the key was rotated straight away.
- **Test 1, overhead (2026-10-29)**, the paired run `20261029T070147Z-compare-ad9b2b` and the notebook (`results/summary.md` has the table):
  - **Kong's own time is 1–3 ms a request** (`latencies.kong` in its log, median 1 ms on every model route). The rest of every delta is outside Kong's code.
  - **Claude (pass-through): +22 and +33 ms TTFT p50**, p50 −11 to +99 ms: the extra hop, not processing. Not comparable with LiteLLM's or Bifrost's translated Claude.
  - **Gemini: +0.7 to +1.0 s in every cell, all of it upstream, not in Kong.** The likely cause is thinking, at its default level through Kong: a median of 137 thinking tokens (81–241) over the ten prompts in the notebook, against 0 direct at `LOW`. A Kong result, not proxy cost (Confounds).
  - **Thinking cuts answers short.** One answer in ten stopped at the 256 cap, reported as `finish_reason: "max_tokens"`, not OpenAI's `"length"`: Kong lower-cases Gemini's reason for a non-streaming answer (`gemini.lua:417`) and passes it through unchanged in a stream (`MAX_TOKENS`).
  - **Kong keeps only the first text part** of Gemini's answer (`gemini.lua:415`, `:112` for streams); the harness joins them all. A second, untested reason Kong's Gemini answers were shorter in the run (30–32 of 100 under 40 characters, 21–23 direct).
  - **Gemini streams arrive in one burst:** first and last chunk at most 5 ms apart over 200 streams (about 125 ms direct), so TTFT equals the whole response time; the notebook's one agent stream looked the same; no usage chunk. Kong calls `streamGenerateContent` without `alt=sse` (`gemini.lua:639`), so Vertex streams a JSON array that Kong re-frames as SSE (`shared.lua:460`); the `enable-buffering` filter skips stream mode, so that isn't it. Whether Vertex or Kong holds the answer back is untested (a direct `streamGenerateContent` without `alt=sse` would tell).
  - **Kong's log computes `total_tokens` as prompt + completion,** so its usage and cost leave out thinking (one request: 111 tokens in the response, 38 in the log). Thinking can only be read from the response's `total_tokens`.
  - **Tail and timeout:** Gemini c1 p95 14.2 s against 4.8 s direct (8 of 100 requests over 12 s, 1 direct), all spent upstream; one request got Kong's 504 "The upstream server is timing out" at the service's 60 s `read_timeout`.
  - **Agent path** (`…111106Z-compare-57e61c` with the agent on Kong, `…112207Z-compare-b0deb8` with it on direct; 20 a cell): Kong's share on Claude +20 to +44 ms, in line with the harness → Kong figure; Gemini +0.75 to +1.3 s, the same thinking effect (Kong drops the agent's `reasoning_effort` too). The agent's usage through Kong has no thought count, so its `think tok` 0.0 means unknown. Three agent → Gemini streams in 160 stopped at `MAX_TOKENS` (two through Kong, one direct).
  - **Cold start:** the first call after scale-to-zero took 14.5 s, of which Kong logged 2.4 s upstream and 56 ms of its own; about 12 s is Cloud Run starting the instance.
  - **Log rows for Claude** carry no `ai` field, but Vertex's own counts arrive as response headers (`internal-input-tokens`, `internal-output-tokens`) that Kong ignores. Kong's services keep the default `retries: 5` (upstream connection retries): relevant to test 2.
- **Test 2, routing and failover (2026-10-31)**, `20261031T143429Z-scenarios-kong-failover-deef82` and the notebook, with a decK window of extra routes (`results/summary.md`):
  - **No failover, confirmed.** A broken model's 404 reached the caller with nothing else tried, on both models and streaming. Routes are chosen by path and headers; a request naming another model gets Kong's 400 `cannot use own model`, a native path with no route a 404 `no Route matched`.
  - **Errors aren't translated.** The OpenAI-format Gemini route returns Vertex's error body; a failed stream, on either model, returns Vertex's JSON-array error with the 404 status; the body names the Vertex model path with the project id. `X-Kong-LLM-Model` is absent on errors.
  - **Retries are connection-only, to the same address.** An upstream refusing connections logged 6 tries (1 + `retries: 5`) to `127.0.0.1:9`, then a 502 "invalid response" (12–15 ms in Kong's log). A 404 got one try; test 1's 504 one 60 s try. Kong's template keeps nginx's `proxy_next_upstream` default (`error timeout`, no non-idempotent requests once sent).
  - **`ai-proxy` sets the upstream target itself** (`kong.service.set_target`, `gemini.lua:683`; in `preserve` the request's own path is sent, `shared.lua` `override_upstream_url`), so `upstream_url` sets only the host and a test route's path must name its model.
  - **Kong's OpenAI stream chunks carry no `model`** (`gemini.lua:108`, `handle_stream_event` builds them with `choices` only; the combined response kept for logging leaves it nil too, `normalize-sse-chunk.lua:178`); non-streaming answers carry the configured model name. Seen in test 1's streams, not in test 2 (no healthy Gemini stream case).
- **Test 3, cost control (2026-10-31)**, four `run-cost.sh` runs (`…183502Z…` rpm, `…183701Z…` race, `…183801Z…` model limit, `…190201Z…` caps) and the notebook, each with a throwaway consumer made through the Admin API, tagged `agw-throwaway` so decK ignores it (`results/summary.md`):
  - **Request counts only.** `rate-limiting` per consumer, or per consumer and route (a per-model limit), in fixed clock windows; a refusal is 429 `API rate limit exceeded` before any model call. Token and cost limits are `ai-rate-limiting-advanced` (enterprise), so OSS has no budget.
  - **Callers see `RateLimit-Limit/Remaining/Reset`, and `Retry-After` on a 429.** Neither LiteLLM nor Bifrost sent quota headers (LiteLLM's rate-limit 429s had `retry-after: 60`).
  - **Bursts overshoot.** The count is incremented after admission in `timer_at(0, …)` (`rate-limiting/handler.lua`): 9 of 10 at once got through a limit of 3 in the notebook; in the recorded run exactly 3 did, by timing, each having seen a count of 0 (`RateLimit-Remaining: 2` on all three).
  - **Gemini's per-request cap is the route's,** whatever the caller sends, and thinking fills it (242 and 244 of 256 in the notebook, answers cut mid-sentence). Claude's pass-through takes the caller's `max_tokens` (742 tokens for a 2000 cap).
  - **The logged cost misses thinking:** $0.00013-0.00015 logged against about $0.0021 billed per caps request (15-17×). Nothing acts on it anyway.
- **Test 4, inline screening (2026-11-01)**, three `screening.json` runs (`…105428Z…` A committed, `…163116Z…` B `ai-prompt-guard` window, `…172636Z…` C `ai-request-transformer` window) and the notebook (`results/summary.md`):
  - **Nothing is screened by default.** Run A: PII reached both models and came back; no injection obeyed. Two Gemini answers stopped inside the value at the 256 cap (default thinking), so they class withheld.
  - **`ai-prompt-guard` refuses in ~13 ms with a bare 400 `bad request`,** by design not saying why (`guard-prompt.lua`); the `file-log` row has status 400, the consumer and zero tokens, no reason. Our 10 deny regexes blocked all 22 PII and injection cases, a best case since they were written for the case set; base64 and output PII got through, and it can't mask. It can be attached to a consumer (schema; not tested).
  - **`ai-request-transformer` masks on `preserve` routes only.** Claude got `[REDACTED]` for all six PII values. On the translated Gemini route the answer comes back as Vertex's native JSON with a 200 (`normalize-json-response.lua:72` skips translation after a transformer), so all 18 Gemini cases (non-streaming) were unreadable; streaming goes through `normalize-sse-chunk.lua`, which has no such check (not tested). It costs a second model call (median +2.6 s Claude, +3.4 s Gemini), screens nothing but personal data in the request, and can't be attached to a consumer (`no_consumer`). One Claude answer (`inj-base64`) came back as a normal-sized 200 with no text the harness could read; unexplained.
  - **`ai-response-transformer` not tried:** it runs after `ai-proxy` and makes the upstream call itself (`subrequest`), with the caller's remaining headers (the Kong key already stripped by `hide_credentials`), then rewrites the answer with a second LLM call.
- **Test 5, identity and secrets (2026-11-01)**, `run-auth.sh` (`…184431Z…`, 13/13; six throwaway consumers, each lapsed key used once first so it was cached), an echo window (`…184742Z…`, no model call) and the notebook (`results/summary.md`):
  - **Cloud Run, then Kong.** Without an ID token, Cloud Run's HTML 403/401. Past it, `key-auth`: 401 `No API key found in request`, or 401 `Unauthorized` with `WWW-Authenticate: Key` for an unknown, expired, deleted or rotated-away key (one message for all); `acl`: 403 `You cannot consume this service`. 12-18 ms; no key echoed.
  - **Lapsed keys leave the cache at once** (one instance; others within `db_update_frequency`) (delete invalidates the entry; `ttl` sets its lifetime). No inactive state and no per-key model list: an ACL group or a consumer-scoped `request-termination` stands in. Rotation is by hand (as on LiteLLM OSS): two keys on a consumer, then delete the old.
  - **Kong forwards the caller's headers upstream** (header names seen by a loopback sink through the same plugins; Vertex itself not observed): the ID token (claims intact, signature replaced), custom headers, `X-Forwarded-For`/`X-Real-IP`/`Forwarded`, and Kong's `X-Consumer-*`/`X-Credential-Identifier`, on both routes. A `request-transformer` could drop the ordinary ones, not `X-Forwarded-*`/`X-Real-IP` (set by the nginx template). `Authorization` is Kong's Google token (`ai-proxy` overwrites the key's header; `hide_credentials` strips it too).
  - **Keys are stored in clear** (`key-auth-enc` is enterprise) and reach Postgres by decK, not the container. A `key-auth` 401 is logged with no consumer; `acl` 403s name it.
- **Test 6, audit fidelity (2026-11-01)**, `run-audit.sh` runs A (`…191325Z…`, committed) and B (`…191644Z…`, `log_payloads` window) and the notebook (`results/summary.md`):
  - **One `file-log` row per request, refusals included,** found by the returned `X-Kong-Request-Id` and joined to Cloud Run's request log by the `X-Cloud-Trace-Context` the row keeps (exact, not by time). The 404 (no route) row has no route, service or consumer.
  - **The row keeps the request headers** (up to 100, `pdk/log.lua`), so a caller's own tags group its requests with no gateway feature. The caller is the consumer; no log names a Google identity, because `kong.yaml` overwrites the ID token (a custom field could log its `email` claim instead; not tried). The agent hop joins by consumer and time only (its trace is new).
  - **Content only with `log_payloads`** (needs `log_statistics`): the request Kong sent upstream and the answer, except a streamed Claude answer or a refused request's; Claude rows log 0 tokens (Anthropic's usage fields aren't read in this config). In Cloud Logging (30 days), not a store of Kong's.
  - **No credential reached a row.** The serializer always redacts `Authorization` (Kong's own Google token on model rows, the caller's key on the 404); only the ID token needs our config (the custom field), or its claims would be in every row.
  - **Admin changes are request rows** (consumer, method, path, no body); no admin audit log in OSS.
- **Rollout gap:** after the review revision's rollout, Cloud Run answered 429 "no available instance" and started no instance for about 7 minutes (18:56 to 19:03 UTC), with no container logs in between. Cause unconfirmed (max 1 instance with Direct VPC egress is the difference from LiteLLM and Bifrost).

## Confounds

- **Thinking differs from the baseline for Gemini** (default level instead of `LOW`). Test 1's Gemini overhead number includes extra thinking time, which can't be separated from Kong's own overhead in a paired run. Report it as a Kong result, not as pure proxy overhead. Measured in test 1: +0.7 to +1.0 s, with a median of 137 thinking tokens against 0 direct, while Kong's own time was 1–3 ms.
- **Claude through Kong is measured in native format,** like the baseline. Kong adds a hop and a token fetch but no translation, so Kong's Claude overhead is not comparable with LiteLLM's and Bifrost's translated Claude overhead.

## Decided (2026-10-25)

Option A and the Bearer keys are in ADR 0014; the database, decK, the startup wrapper and throwaway keys in ADR 0015, which replaced the first plan (DB-less, keys by redeploy).

- **Kong on Postgres, config by decK.** Above (Config model).
- **Throwaway keys (tests 3, 5, 6) come from the Admin API.** A run script creates a consumer and key with a `ttl` through `/admin-api`, without the `agw` tag, so decK neither deletes nor reports it (key held in an env var, never on disk), runs the cases, and deletes them on exit; a key it fails to delete expires. Config windows (ADR 0010) are a decK sync of a `TEST ONLY` `kong.yaml`, then a sync of the committed one.
- **Callers keep `Authorization: Bearer <key>`.** `key-auth` gets `key_names: [authorization]` and `hide_credentials: true`, and each credential is stored as the literal string `Bearer <key>`, so the agent and harness send the Kong key exactly as they sent LiteLLM's and Bifrost's.

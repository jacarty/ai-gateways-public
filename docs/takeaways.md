# Takeaways: what each gateway turned out to be good at

What I took away from running the three gateways, condensed from the matrix in [`results/summary.md`](../results/summary.md#across-the-three-gateways). These are notes from a learning lab, not a recommendation: one small setup, short runs, and whatever surprised me along the way. Scope: the OSS editions of LiteLLM v1.103.2, Bifrost `transports/v2.2.6` and Kong OSS 3.9.3, each on one Cloud Run instance, in front of Gemini 3.8 Flash and Claude Haiku 5.5 on Gemini Enterprise Agent Platform (`eu`), for agent-to-model traffic. Every row rests on what was run here; where a row also leans on source or vendor docs, it says so. Releases move: check a row against the release you would deploy.

| If you want… | Worked on OSS | Why (test) | Watch out for |
| --- | --- | --- | --- |
| **Failover between Gemini and Claude in the gateway** | LiteLLM, Bifrost | Both failed over both ways, streaming too, and told the caller which model answered (2) | A fallback keeps the caller's parameters: Claude → Gemini ran Gemini at its default thinking level on both (2). Bifrost's rule fallbacks can't be opted out of; LiteLLM's can (`disable_fallbacks`). Kong OSS has none (`ai-proxy-advanced` is enterprise) |
| **Enforced spend budgets per team or caller** | LiteLLM; Bifrost, with burst overshoot | Hard budgets and rate limits per key, refused before the model is called (3) | How far a budget can be overshot differs: LiteLLM reserves each request's worst case, so a burst is refused early and spend ends at most one request over (0.3–8.5% in test 3); Bifrost doesn't reserve, so its real ceiling is the limit plus one burst (3.1× a budget with ten at once). Prices were wrong when checked (LiteLLM's bundled map and Bifrost's live datasheet had Gemini 3.8 Flash at half price; Bifrost adds no regional uplift): set them by hand (ADR 0009). Kong OSS counts requests only, with no budget |
| **Per-model budgets on one key** | Bifrost | OSS in Bifrost (3) | Enterprise in LiteLLM (`model_max_budget`, test 7). Kong OSS has per-model *request* limits only |
| **Inline PII masking and injection screening without a licence** | LiteLLM | Built-in content filter masked PII both ways; the LLM judge blocked every injection (4) | Guardrails are global on OSS, so every caller is screened alike; the judge adds seconds per request, fails open and its spend is invisible to budgets and the ledger (4, 6). Kong OSS has a regex deny list and an LLM rewrite that breaks its translated Gemini route; Bifrost OSS screens nothing and silently ignores a guardrail config |
| **Low added latency** | all three, warm, on Claude; not Kong on Gemini | Bifrost's overhead was indistinguishable from zero; LiteLLM +20–30 ms at concurrency 1; Kong's Claude pass-through +20–40 ms, of which Kong's own time 1–3 ms (1) | No ranking: each gateway was paired with direct on a different day, and Kong's Claude was a pass-through where the others translated. LiteLLM's overhead rose with concurrency on one worker (+50–65 ms at 5), a sizing effect as much as LiteLLM's. Through Kong, Gemini was 0.7–1.0 s slower, likely default thinking, because Kong drops `reasoning_effort` and `max_completion_tokens` (1). Cold starts are separate: tens of seconds on LiteLLM and Bifrost |
| **OpenAI-format clients calling Claude on Vertex** | LiteLLM, Bifrost | Both translated OpenAI requests to Claude on Vertex (1) | Kong OSS can't: its Claude route is a native `rawPredict` pass-through, so callers send Anthropic format (ADR 0014) |
| **A request log you can join to Cloud Run and Cloud Logging** | Kong, LiteLLM | Kong: a `file-log` row per request, refusals included, in Cloud Logging, joined by trace; LiteLLM: a spend-log row per request, refusals included, joined by trace, but none for its LLM judge's calls (6) | Settings that store credentials: LiteLLM's `store_prompts_in_spend_logs` stores ID tokens; Bifrost's `logging_headers` can store keys and ID tokens; Kong logs the ID-token header unless overwritten, as our config does (6). Bifrost stores prompts and answers by default for 365 days, and some refusals leave no row |
| **Already running Kong for APIs** | Kong | Same consumers, ACLs and plugins, scoped to a consumer, a route or both, which stood in for a Claude-only key and a per-model limit (3, 5, 7) | It forwards nearly every caller header to the model (5); it stores keys in clear (`key-auth-enc` is enterprise); the AI controls (failover, token limits, PII) are enterprise (7) |
| **Key rotation without a licence** | Bifrost (manual rotation built in; scheduled rotation is enterprise); LiteLLM and Kong by hand | Bifrost rotated a key in one operation and refused the old value at once (5) | On LiteLLM (`/key/regenerate` is enterprise) and Kong, rotate by adding a new key and deleting the old one, with both accepted in between (5) |
| **An explicit refusal when you configure an enterprise plugin** | Kong | An enterprise plugin fails validation by name (7) | Kong's message reads like a config fix ("add it to the 'plugins' configuration property") though there is no code to enable, and its enterprise API routes are a plain 404. Bifrost accepts and ignores enterprise config, and its enterprise API routes answer HTTP 200 with the UI page; LiteLLM's gates fail four ways, one silent (an empty audit log) (7) |
| **The caller's Google identity as the principal (JWT, SSO, OIDC), RBAC or an admin audit log** | none on OSS | Enterprise on all three: LiteLLM's JWT auth, Bifrost's SSO, Kong's `openid-connect`, and each one's admin audit log (7) | On OSS the caller is a bearer key per caller; let Cloud Run IAM decide who can reach the gateway, keep keys in Secret Manager, and audit admin changes through the scripts and Terraform that make them. Kong's OSS `jwt` plugin checks tokens against keys set per consumer, not Google's (not tried), and Cloud Run replaces the ID token's signature; a `pre-function` could map its claims to a consumer (not tried) |
| **Restricted egress or least-privilege access** | none tested; Bifrost needs the most care | Bifrost downloads its model catalog and prices from getbifrost.ai on every cold start (about 22 s of a ~28 s start; a live file, not part of the release). Each gateway's service account held project-level `roles/aiplatform.user`, which reaches every model in the project, not only Gemini and Claude. LiteLLM's and Bifrost's Cloud SQL had a public IPv4 (encrypted connections only); Kong's had a private IP only (ADR 0016) | Pin or mirror Bifrost's catalog (`pricing_url`) before blocking egress. Agent Platform IAM is not per model, so give a gateway a project of its own if it must reach only some models. Put each database on a private IP |

## In short

- **LiteLLM** is the most complete set of AI controls on OSS: failover, hard budgets, PII masking and an LLM judge. It charges for governance across many callers (per-key policy, identity, rotation, the admin audit log). It's the one to play with if you want the gateway itself to *do* the screening and spend control; give it more than one worker under concurrency.
- **Bifrost** added no measurable overhead and has the fullest budgets on OSS, per model included, plus rotation. It has no screening at all on OSS, and its paid gates are silent. It shines at routing and spend control at low overhead; screening has to live elsewhere.
- **Kong OSS** is a mature proxy with AI translation, a complete joinable request log and flexible plugin scoping, but its AI controls (failover, token limits, PII) are enterprise. It makes most sense if you already know Kong and want model traffic under the same consumers and logs; failover and screening stay in the caller.

## Not covered

One instance per gateway (`max_instances = 1`), so no multi-instance counters, high availability or sustained load (overhead was measured up to concurrency 5; behaviour tests sent bursts of up to 12); two models on one platform; agent-to-model traffic only (no MCP, A2A or ingress); no paid edition was tried, so what the paid tiers do is from source and vendor docs, not tested.

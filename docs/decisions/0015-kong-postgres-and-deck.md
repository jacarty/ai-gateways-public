# 0015. Kong: Postgres, decK as source of truth, throwaway keys through the Admin API

- Status: Accepted
- Date: 2026-10-25
- Supersedes: ADR 0014's throwaway-keys-by-redeploy decision and its rendered-config consequence. ADR 0014's Claude path and Bearer keys stand.

## Context

ADR 0014 assumed Kong would run DB-less: the declarative file is the whole config, the Admin API can't create entities, so every throwaway key needs a redeploy and the rendered config holds key values. After this project the lab will run all three gateways side by side for further testing, so Kong should have the same shape as LiteLLM and Bifrost: a database, keys created and deleted at runtime, and no redeploy per key.

With Postgres, Kong 3.9.3 needs its schema migrated before it starts, and the database, not a file, holds the config. The built-in `kong config db_import` only upserts (`kong/db/declarative/import.lua`): an entity removed from the file would stay live, the same trap as Bifrost's undeclared sections.

## Decision

- **Kong runs on Cloud SQL Postgres 16** (`db-f1-micro`, zonal, no backups), reached over TCP on a private IP (ADR 0016; Kong's `init` phase can't use Cloud Run's Cloud SQL socket). The stack has `make start-`/`stop-kong` like the others.
- **decK is the config's source of truth.** `config/kong.yaml` is committed without secrets: keys come from `${{ env "DECK_…" }}` at sync time. `deck gateway sync` creates, updates and deletes entities to match the file, scoped by a select tag so test entities are left alone.
- **The Admin API is reached through a Kong route.** A service pointing at the loopback Admin API (`127.0.0.1:8001`) and a route `/admin-api`, behind Cloud Run IAM, then `key-auth` and `acl` (group `admin`). decK, `make status-kong`'s live-config check and the test scripts use it with the admin key (`agw-kong-admin-key`).
- **A startup wrapper runs migrations and bootstraps the admin route.** The container command runs `kong migrations bootstrap`, `up` and `finish`, then `kong config db_import` of a small bootstrap file (the admin service, route, consumer, ACL group and key, and the global `key-auth`, with fixed IDs, so a re-import on each start is an upsert), then `exec`s the image's entrypoint. `config/kong.yaml` declares the same entities, so a sync keeps them. A separate migrations job (Kong's advice for clusters) isn't needed at one instance.
- **Throwaway keys (tests 3, 5, 6) are created through the Admin API**, tagged and given a `ttl`, and deleted on exit, as on LiteLLM and Bifrost (ADR 0010). A key a script fails to delete expires on its own.

## Consequences

- One more tool on the workstation: decK, pinned to a release at least two weeks old.
- The Admin API is reachable from outside the container, behind IAM and an admin key. A leaked admin key can rewrite the gateway's config: it stays in Secret Manager and is read into a variable only.
- A database to start, stop and pay for while the stack is up; `make destroy-kong` needs it running.
- The wrapper (`config/start.sh`) picks the migration step from `kong migrations list`'s exit code (0 up to date, 3 bootstrap, 4 finish, 5 up then finish), so it doesn't depend on `bootstrap` being repeatable. The `unix:/cloudsql/…` socket failed in the hand-build (Kong's `init` phase can't open it); ADR 0016 moved Kong to a private IP over TCP.
- Kong's log serializer redacts only `Authorization` and `Proxy-Authorization`; `file-log` redacts the callers' ID token (`X-Serverless-Authorization`) with `custom_fields_by_lua`.
- The `no-test-window` hook still guards `config/kong.yaml`; a window is now synced with decK rather than redeployed.

## Alternatives considered

- **DB-less (ADR 0014):** simpler, but a redeploy per throwaway key, keys rendered into the config, and a different shape from the other gateways when all three run together.
- **`kong config db_import` as the source of truth:** removed entities would survive.
- **decK baked into a custom image, syncing over loopback at start:** no exposed Admin API, but every config change is an image build, and runtime keys would still need the Admin API.

## Addendum (2026-10-28): Kong Manager on

Kong Manager OSS (the admin UI bundled in the image) is turned on, so the three gateways' interfaces can be compared. It has no login of its own and calls the Admin API from the browser, so it can't send `/admin-api`'s key. Kong serves it on loopback at `/manager`, with its Admin API calls on a second route, `/manager-api`. Both routes take no key; Kong's OSS `basic-auth` plugin gives the browser's username and password prompt (user `admin`, password generated by Terraform into `agw-kong-manager-password`, stored hashed by Kong), the same login shape as LiteLLM's and Bifrost's UIs. Cloud Run IAM still applies first. An identity check on the Google ID token Cloud Run forwards was possible (Cloud Run verifies it and rejects a forged one) but left out to match the other two. Entities changed in Manager carry no `agw` tag, so decK neither deletes nor reports them; changes go through `kong.yaml`.

Three further decisions came out of making it work and of its review:
- **Kong serves Manager's `kconfig.js` itself.** Manager 3.9.0.0 can't take a relative API URL. The served file uses the page's own host, so Manager isn't tied to one port or domain.
- **`/` redirects to `/manager`** with a relative `302` from a `pre-function`. Kong's `redirect` plugin needs an absolute URL, which would leave the proxy.
- **Cross-site protection on both Manager routes.** A `pre-function` refuses browser-marked cross-site requests and non-JSON writes, and drops `Origin`, because the Admin API grants CORS to any origin with credentials.

The Manager password is as powerful as the admin key. Because decK can't compare a hashed password, `deck.sh` derives the credential's id from the password and deletes the stale credential before a sync, so a rotation takes effect.

# 0014. Kong: Claude as a native pass-through, Bearer keys, throwaway keys by redeploy

- Status: Accepted; the throwaway-keys-by-redeploy decision and the rendered-config consequence are superseded by ADR 0015 (Kong on Postgres)
- Date: 2026-10-25

## Context

Kong OSS 3.9.3 runs DB-less: the declarative file is the whole config, the Admin API is read-only except `POST /config`, and consumer keys cannot use a vault reference. Three things from the Phase 3 Understand step (`gateways/kong/NOTES.md`) differ from LiteLLM and Bifrost and were not settled before:

- `ai-proxy` cannot translate an OpenAI request to Claude on Vertex. The `gemini` provider only builds `publishers/google` URLs, the `anthropic` provider has no GCP identity and the wrong body shape, and Vertex's OpenAI-compatible endpoint does not serve Claude in `eu`.
- `key-auth` compares the whole header value and does not strip `Bearer `, while our callers send `Authorization: Bearer <key>`.
- ADR 0010's throwaway keys for tests 3, 5 and 6 are minted through a gateway API. Kong has no per-entity write API in DB-less mode.

## Decision

- **Claude goes through Kong untranslated (option A).** A `provider: gemini` route with `route_type: preserve` and `model.options.upstream_url` set to the Claude `:rawPredict` URL (a second route for `:streamRawPredict`). Kong adds its own GCP token and forwards the caller's Anthropic body unchanged. The agent's Claude client and the harness's `direct` rawPredict request point at Kong; Gemini stays on the OpenAI `/chat/completions` path. The lost translation, token statistics and cost for Claude are recorded as test 7 findings, not worked around.
- **Callers keep `Authorization: Bearer <key>`.** `key-auth` uses `key_names: [authorization]` and `hide_credentials: true`, and each credential is stored as the literal string `Bearer <key>`. Agent and harness send the Kong key as they sent LiteLLM's and Bifrost's.
- **Throwaway keys come from a redeploy.** A run script renders a `TEST ONLY` window config with the throwaway consumer and key (held in an env var, piped to `gcloud secrets versions add --data-file=-`, never on disk), deploys it, runs the cases, redeploys the committed config and checks the live config is clean. The Admin API stays on loopback.
- **Keys for the agent and harness are generated by Terraform** and rendered into the `agw-kong-config` secret, as for Bifrost (ADR 0013).

## Consequences

- Claude through Kong is an authenticated proxy, not an AI-aware one. Its overhead in test 1 is not comparable with the translated Claude overhead of LiteLLM and Bifrost.
- The agent and harness need a native-Claude gateway mode for Kong; this is environment-driven, with no per-run code change.
- The rendered config holds key values, so it is a secret and the stack's Terraform state holds it too (private state bucket).
- Each throwaway key is a deploy: it can fail an in-flight request with `max_instances = 1`, so never run one during a measured run. Tests 3, 5 and 6 are slower to set up than on the other gateways.
- The `no-test-window` hook still stops a window from being committed.

## Alternatives considered

- **Translated Claude via Vertex's OpenAI-compatible endpoint:** not served for Claude in `eu`.
- **`anthropic` provider with static auth:** wrong body shape for Vertex, and an access token expires within an hour.
- **Custom Lua (`pre-function`) to translate:** a home-made translator would measure our code, not Kong.
- **A separate key header (for example `apikey`):** changes the agent and harness for one gateway and weakens comparability.
- **Reuse the harness key with lowered limits (ADR 0010's rejected option):** changes the key measured runs depend on.
- **Expose the Admin API to POST throwaway config:** needs a routed, authenticated Admin API, and `POST /config` replaces everything anyway.

### What the baseline says

- **Claude is the stable signal.** p50 0.48–0.49 s and TTFT ~0.27 s on every direct cell, in both runs. Through the agent, p50 moves by −4 to +45 ms and TTFT by +2 to +55 ms. Gateway overhead will be clearest on Claude.
- **Gemini's latency drifts over time, so only same-time comparisons are fair.** Gemini 3.8 Flash on `eu` has 8–31 s outliers on direct calls with no thinking. Its tail also moved a lot between the two runs (below), and within run 2 the agent cells (run ~20 minutes after the direct ones) were *faster* than direct. Cells run one after another, so they absorb that drift. Compare gateways on Gemini p50 and TTFT p50, and only against a direct baseline measured in the same job.
- **Thinking differs slightly by path.** Direct Gemini never thought (0/799 successful requests in this run, 0/800 in run 1); through the agent, 1–4 requests in 50 used some thinking (up to 180 tokens), probably because ADK adds its own system-prompt text. Consistent across both runs.
- **1 request timed out** (`direct-gemini-stream-c1`, `ReadTimeout` at 60 s), the same Gemini tail past the limit. Run 1 had 2 such timeouts on the agent path.
- Agent rows have 50 requests per cell (direct: 200), so their p95/p99 rest on few samples.

### Test 2: routing and failover

**Runs:** `scenarios scenarios/litellm/failover.json`, 29 requests each, one at a time, local runs with the harness's virtual key on 2026-10-18: [`…071745Z…`](raw/litellm/20261018T071745Z-scenarios-litellm-failover-f5141c/) with LiteLLM's mock switches off (the default; revision `00003`) and [`…074115Z…`](raw/litellm/20261018T074115Z-scenarios-litellm-failover-3ea349/) with `dangerously_allow_mock_testing_request_params` on for the test window (revision `00004`, reverted afterwards). Config for the test window only: `router_settings.fallbacks` Gemini ↔ Claude and `test-gemini-broken` → Claude, retries off; the committed config has no fallbacks, so measured runs (test 1 and any later `compare`) keep comparing a model against itself, and any LiteLLM run must say which it used. These are behaviour runs from the workstation, not measured ones: their latencies are indicative only. How to repeat it, automated or by hand: `harness/scenarios/litellm/README.md`.

| Case | Mocks off | Mocks on | What the caller sees |
| --- | --- | --- | --- |
| Healthy Gemini (before and after) | 200, Gemini (4/4) | 200, Gemini (4/4) | `attempted-fallbacks: 0` |
| **Real upstream error** (`test-gemini-broken`, a model id that does not exist) | **200, Claude (8/8)** | **200, Claude (8/8)** | `model: claude-haiku-5-5`, `attempted-fallbacks: 1`; streaming too |
| Forced 500 on Gemini | 400, refused | **200, Claude (6/6)**, streaming too | `model: claude-haiku-5-5`, `attempted-fallbacks: 1` |
| Forced 500 on Claude | 400, refused | **200, Gemini (3/3)** | `model: gemini-3.8-flash` |
| Forced 500, `disable_fallbacks: true` | 400, refused | **500 (2/2)** | the raw error: the caller can opt out |
| Forced 429, either model | 400, refused | 429 (6/6) | see below |

- **Failover works and is visible.** On a real upstream error and on a forced 500, in both directions and when streaming, the request is answered by the other model, and the response says so: its `model` field names the model that answered (not the one asked for) and `x-litellm-attempted-fallbacks` counts the hops. A caller that wants the error instead sets `disable_fallbacks`. Once warm, a failed-over request took 0.35–1.3 s when Claude answered and 1.9–3.4 s when Gemini did, in line with the fallback model on its own; the first one on each new revision took 15–20 s (the first-Claude-call cost, `gateways/litellm/NOTES.md`).
- **Callers can't force failover unless the operator allows it.** The mock switches are refused (400) by default and can only be enabled in `config.yaml`. A good default for a shared gateway.
- **429s do trigger failover, but the mock can't show one succeed.** The 429 mock is carried into the fallback request, so the fallback model "rate-limits" too. LiteLLM records the fallback targets it has tried for a request and doesn't revisit them, so the request went Gemini → Claude and stopped (about 30 ms, no model calls), returning the 429. Two-way fallbacks therefore don't loop: when both models fail, a request costs one attempt each. A real 429 can't be forced cheaply; test 1 saw real upstream 429s, but without fallbacks configured.
- **A fallback keeps the original request's parameters.** Seen by hand in `gateways/litellm/tests.ipynb` (its curl cells, 2026-10-18, mocks on; one request, so indicative): a Claude request with a forced 500 was answered by Gemini with **58 reasoning tokens** in 1.39 s, while Gemini asked for directly with `reasoning_effort: "low"` didn't think and answered in about 1.0 s. The Claude request carried no `reasoning_effort` (thinking is off for Claude), LiteLLM passed the body on unchanged, and Gemini thought at its default level. A fallback model runs with whatever the caller wrote for the first one: thinking, caps and other model-specific settings don't adapt, so a failed-over answer can cost more and take longer than the same model asked for directly. Per-model defaults in `config.yaml` (`litellm_params`) may be the operator's lever (*not tested*).
- **Error bodies show callers the fallback configuration.** `litellm.expose_router_debug_in_errors` is on by default, so a failed request's error lists the configured fallback groups ("Available Model Group Fallbacks=['claude-haiku-5-5']"). A small information leak for a shared gateway; noted for test 6. A mocked 500 with `disable_fallbacks` went further: its message listed the whole fallback map, every group including the test model. That text comes from the mock exception itself, so real errors may not do it.
- **Audit note for test 6:** for Gemini, `x-litellm-model-api-base` reports `eu-aiplatform.googleapis.com`, while LiteLLM's request code calls `aiplatform.eu.rep.googleapis.com` (a reporting helper builds `<location>-aiplatform…` for every location). Claude's is reported correctly.
- **Not tested here:** failover through the agent. The agent can't add mock fields, and it only asks for the two real models; with fallbacks on, an agent request would fail over the same way (the gateway decides), but that is unverified.

| Tokens per minute, 6 at once | same | 3 admitted, 3 refused (122 left); the 3 used ~330 tokens | Hard; reservations refuse requests the limit could serve |
| A cap above the limit | same | `max_completion_tokens: 2000` refused on an empty window, no model call | Hard |
| Dollar budget, one at a time | `max_budget: $0.0002` | 6 × 200, then 429 "Budget has been exceeded!" for every model; final spend $0.00020053 and $0.00021703, and $0.00021373 and $0.00020713 in two notebook runs: 0.3–8.5% over | **Hard**, overshoot at most one request |
| Dollar budget, 10 at once | `max_budget: $0.0005` | 4 admitted, spend $0.00013–0.00014 (25–29% of the budget; CLI and two notebook runs); a second burst: 3 more | Hard, no overshoot; under-uses the budget |
| Budget reset | `budget_duration: "1m"` (notebook) | two notebook runs: spend stayed 3–4 minutes past `budget_reset_at` (14:14, 14:37), then cleared | Resets on a ~10-minute job tick, not on time |
| Throttle instead of block | `rpm_limit: 4`, `throttle_on_budget_exceeded`, window config | over budget, the key kept working at 2 requests a minute ("Current limit: 2") and spent 7× its budget in a minute | **Advisory**: a slowdown, not a cap |
| Unpriced model | `max_budget: $0.00001`, window config | once over budget, the unpriced model was refused like the priced one | Hard: no price is not "free" |

- **Every LiteLLM cost control on a key is hard, and OSS.** Budgets and rpm/tpm limits refuse with a 429 before the model is called, in about 20 ms. The one advisory mode is opt-in: `throttle_on_budget_exceeded` plus a global `budget_exceeded_throttle_percentage` turns an exhausted budget into a reduced rate, and spend then grows without a bound. `throttle_on_budget_exceeded` without the global setting is a plain block (the hand run before the window).
- **Limits work by reservation, so they err towards refusing.** Before a call, LiteLLM reserves its worst case against the key's counters: input tokens plus `max_completion_tokens` for TPM, that times the price for budgets. After the call it settles to the real figure. One at a time this costs the last reservation's worth of headroom; at once it refuses requests that would have fit (a quarter of a budget spent when the burst was refused). The upside is that concurrency never overshoots a budget; the one overshoot is the last request admitted with a shrunk reservation, at most one request's cost. A caller can get more through a limit by asking for a smaller `max_completion_tokens`.
- **A budget is only as right as the price.** LiteLLM v1.103.2's price map has every Gemini 3.8 Flash tier at **half** Google's catalogue price ($0.75 / $3.75 per 1M standard, against $1.50 / $7.50), so budgets would have let through twice their value in Gemini spend. `config.yaml` now sets the catalogue's regional price ($1.65 / $8.25); the notebook's price check then matched LiteLLM's cost to tokens × price exactly for both models. Haiku 5.5 isn't in the map at all and isn't in the public SKU catalogue either; its price comes from the pricing page (EU multi-region $0.11 / $0.55, global $0.10 / $0.50). LiteLLM skips budgets only for a model priced at exactly 0; one with no price is treated as having a cost (whether its requests then record $0 of spend wasn't tested: none got through).
- **`x-litellm-key-spend` is not a running balance.** It is the spend saved to Postgres (batched every ~10 s) plus the current request, so in a burst each response shows little more than its own cost. Enforcement uses the live counter: every one-at-a-time budget refusal's "Current cost" equalled the exact sum of the admitted requests. A refusal from the reservation path during a burst reports spend **plus in-flight reservations** instead ($0.00057–0.00108 in the race run, against about $0.00013 actually spent), so the figure in a 429 depends on which check refused it.
- **No quota headers.** LiteLLM v1.103.2 sent no `x-ratelimit-remaining-requests` / `-tokens` on any response, so a caller learns it is near a limit only from the 429 (which does carry `retry-after: 60` for rate limits; budget 429s carry none).
- **`budget_duration` is coarse.** Spend is reset by a job that runs about every 10 minutes for keys whose `budget_reset_at` has passed, so a short window resets late (here 3–4 minutes late).
- **Refusals say who you are.** A budget 429 names the key alias and the key's last four characters; a rate-limit 429 gives the key's hash. Two code paths refuse budgets: the check at auth (~20 ms, alias) and the reservation (0.1–0.8 s in a burst, hash). The hashes are redacted in the committed runs. Noted for test 6.
- **OSS ceiling.** Per-model budgets on one key (`model_max_budget`) are refused at key creation with a **500**; tags (and tag budgets) with a 403; `enforced_params` (e.g. forcing every caller to send a `max_tokens`) is accepted at key creation and then every request with the key fails with a 500. So a single key can't hold separate Gemini and Claude budgets, and callers can't be forced to cap their output, without a licence; separate keys per model and the reservation's dependence on `max_completion_tokens` are the OSS workarounds.

- **The models already resisted the injections; they didn't protect PII.** With no gateway at all, neither model obeyed any of the six injections (no canary came back; the answers refuse or simply answer the harmless part), but both repeated 11 of 12 PII values and Gemini volunteered the test card. For these models and cases, the gateway's job is PII, not injection; a weaker or older model may differ, which is why the case set stays the same for every gateway.
- **The built-in content filter is OSS, in-process and effective on PII with a known shape.** Every PII value was replaced before the model saw it (`[EMAIL_REDACTED]` and so on) and the two values the models wrote were masked on the way back, with no false positives on near-misses ("What is an IBAN used for?") and no measurable latency. UK mobile and NI numbers needed custom regexes (no prebuilt pattern). Masking changes the conversation: Claude saw the placeholder and asked the user to resend the number, so the caller sees the masking indirectly.
- **Keywords catch the explicit injections and miss the rest.** The filter blocked the three that say what they are and passed the three that don't (exfiltration via a markdown image, an instruction inside a quoted review, a base64-encoded instruction). Its 400 names the category and the rule that fired ("conditional match 'print + system prompt'"), which tells an attacker which words to avoid.
- **The LLM judge caught every injection, at a price.** All 12 were refused, including the indirect and encoded ones, with no false positives on the benign set. But every request waits for an extra model call: +3–4 s typically, and 45 s median on the PII cases, which ran first in both attempts (the judge deliberating or the order of the run; not separated). It **fails open**: if the judge call errors, LiteLLM lets the request through. Its 422 tells the caller the overall score and each criterion's verdict and reasoning. LiteLLM warns that its Gemini call sets `temperature`/`top_p`/`top_k`, which are deprecated for Gemini 3.
- **The judge's cost is not in the caller's cost.** Requests the judge passed reported the same `x-litellm-response-cost` as run A, and blocked requests $0, although a judge call was made each time. Whether the judge's spend reaches the key's budget or the spend logs is for test 6; from the caller's side, screening is free and budgets don't see it.
- **"Blocked, logged or invisible":** B and C blocked (a 4xx before any model call, logged by LiteLLM). B's masking is a fourth outcome: the request goes through, changed, and only the placeholder shows it. Without a guardrail, everything is invisible to the gateway. `x-litellm-applied-guardrails` lists the guardrails that *ran*, so it is on every screened response, blocked or not; it says nothing about whether one acted. The judge's log-only mode (`on_failure: log`) was not run.
- **OSS ceiling.** Everything above ran without a licence. What needs one: attaching a guardrail to a key (so OSS guardrails are global, `default_on`: while a window was open the agent was screened too), tag-based guardrails and dynamic guardrail parameters, and the legacy moderation callbacks (LLM Guard, Llama Guard, OpenAI and Google moderation). The ~50 third-party guardrail integrations (Lakera, Presidio and others) aren't gated but need outside services, and are out of scope.
- **Reading the classes:** "withheld" covers both a masked value the model declined to repeat (B, Claude) and an answer giving a different value (A and C, the output cases: Gemini named another test card, and once an invented SSN). A canary only shows obedience; "passed" injections were read by hand, and none was obeyed.

### Test 5: identity and secrets

**Run:** `scenarios harness/scenarios/litellm/auth.json` via `run-auth.sh`, 2026-10-20, local, revision `00013` (committed config): [`…135214Z…`](raw/litellm/20261020T135214Z-scenarios-litellm-auth-e0f291/), 12/12 cases as expected, 3 of them reaching a model. Repeated by hand in `gateways/litellm/tests.ipynb` ("Test 5"), with the same results, plus read-only `gcloud` checks of where the credentials live.

**Gateway → model: workload identity, and nothing else is possible here.** LiteLLM calls the Agent Platform as its Cloud Run service account (`agw-gw-litellm`) through Application Default Credentials. That account has no user-managed keys, `config.yaml` holds no credentials, and the project's org policy blocks creating service-account keys at all (`iam.disableServiceAccountKeyCreation` and its managed successor, both enforced), so LiteLLM's key-file mode (`vertex_credentials`) isn't an option in this project. Still open from tech debt: the account holds project-wide `roles/aiplatform.user`, every model rather than the two used.

**Caller → gateway: two layers, refusing differently.**

| Credentials sent | Refused by | Status | Body |
| --- | --- | --- | --- |
| nothing | Cloud Run IAM | 403 | HTML "Forbidden" |
| LiteLLM key only | Cloud Run IAM (reads the key as a Google token) | 401 | HTML "Unauthorized" |
| ID token only | LiteLLM | 401 | JSON `auth_error`: "No api key passed in" |
| ID token + a key not starting `sk-` | LiteLLM | 401 | JSON `auth_error`, echoing the key masked (`agw-****-123`) |
| ID token + an unknown `sk-` key | LiteLLM | 401 | JSON `token_not_found_in_db`, echoing the last four characters **and the key's SHA-256 hash** |
| ID token + a Claude-only key, asking for Gemini | LiteLLM | 403 | JSON `key_model_access_denied`: "not available for this API key, or the model name is invalid" |
| ID token + an expired key (`duration`) | LiteLLM | 401 | JSON `expired_key`, with the expiry time |
| ID token + a blocked key (`/key/block`) | LiteLLM | 401 | JSON `auth_error`: "Key is blocked" |
| ID token + a deleted key | LiteLLM | 401 | JSON `token_not_found_in_db`: the same as a key that never existed |
| ID token + the harness's or the agent's key | — | 200 | an answer |

- **IAM keeps the gateway off the internet; the key is the identity inside it.** Anything without an invoker's ID token is refused by Cloud Run before LiteLLM sees it (HTML, in 0.01-0.2 s), so only the agent, the harness and one user can reach the gateway at all. Past that, LiteLLM knows a caller only by the key it presents: the agent's key worked from a user's ID token exactly as from the agent's. A virtual key is a bearer secret; whoever can read `agw-litellm-agent-key` is the agent to LiteLLM (budgets, limits and spend logs follow the key, not the caller's Google identity).
- **Tying LiteLLM's principal to the caller's own identity needs a licence.** LiteLLM's JWT auth (`enable_jwt_auth`: callers authenticate with a signed token, such as a Google ID token, instead of a shared key) is enterprise-only in v1.103.2. So is key rotation (`/key/regenerate`, test 3). On OSS a key is rotated by minting a new one, updating its secret and deleting the old one.
- **Key states are OSS and enforced at once.** Model restriction, blocking, expiry and deletion each refused the next request (one key was blocked and used within a second); each refusal has its own error `type`. A deleted key can't be told from one that never existed, which is the right answer for a caller.
- **Error bodies say a little too much.** An unknown `sk-` key comes back with its last four characters and its SHA-256 hash, which some LiteLLM versions accept in place of the key (not checked for v1.103.2); the harness now redacts hashes before writing results (test 3's redaction work). The model-access refusal is deliberately vague. The HTML-versus-JSON split tells a caller which layer refused it.
- **The gateway's own secrets are all in Secret Manager.** Master key, salt key (which encrypts credentials LiteLLM stores in its database), database URL and the config file are secrets injected into the container; the only plain environment values are the project, the model location and a feature flag. The per-caller keys are secrets readable by their caller's service account. Still open from tech debt: every gateway service account can read every `agw-*` secret.
- **The ID token reaches LiteLLM.** Cloud Run passes `X-Serverless-Authorization` through and LiteLLM doesn't scrub it from request metadata (`NOTES.md`); whether it reaches logs is test 6.

- **The spend log is a good per-request ledger, and it joins the gateway's own logs by itself.** Every request, refused ones included (with error class and code), has a row with the key alias, model, the endpoint actually called, tokens, cost, timings and guardrails. When the caller sends no session, LiteLLM uses the incoming Cloud Trace id as the session id, so each row matches its Cloud Run request-log entry exactly. A caller that sends `litellm_session_id` and `spend_logs_metadata` gets its rows grouped and labelled, refusals included (a refusal can lack the `x-litellm-call-id` header, so the caller's tag is the only way to find its row). The endpoint in the log is the right one (`aiplatform.eu.rep.googleapis.com`); only the `x-litellm-model-api-base` response header is wrong (test 1).
- **The agent hop doesn't join.** The agent's `/run` request and the gateway request it causes carry different traces, the agent sends no session or tag, and its container logs hold neither the session nor the prompt. An agent run can be matched to its gateway rows only by time, key alias and user agent (`AsyncOpenAI/Python` for the agent's client). The fix is on the caller's side and needs no gateway change: the agent could send its ADK session id as `x-litellm-session-id`. Not made in this phase (the agent's code stays fixed); recorded as a recommendation.
- **No log names a Google identity.** The gateway knows the key, not who held it (test 5); Cloud Run's request logs record status, latency, user agent and trace but not the caller; Data Access audit logs are off (the default). The caller IP LiteLLM records is Cloud Run's internal front end (`169.254.x`), useless for attribution.
- **Storing prompts stores credentials.** With `store_prompts_in_spend_logs` on, each successful row keeps the prompt and answer, and also the request's headers: the caller's Google **ID token**, twice (`proxy_server_request.metadata.headers` and its `requester_metadata` copy), and `x-forwarded-for` (the caller's real IP). LiteLLM scrubs its own `Authorization` header (the virtual key) but not Cloud Run's `X-Serverless-Authorization`. Anyone who can read spend logs (the master key, the admin UI) can then collect callers' ID tokens, each usable against this gateway for up to an hour. Don't turn it on behind an ID-token front end without scrubbing that header first. The tokens stored during the window have long expired, and the database goes with the phase-end destroy.

The judged requests' rows also lost the caller's `spend_logs_metadata` and the user agent (the refused request, stopped before the judge, kept both); the session id survived.
- **The ledger can disagree with the caller.** In the notebook's run on D, the agent gave up after 60 s and returned 504, but the gateway call it had made (slow from a cold start, 77 s) completed and was logged as a success with spend on the agent's key. Each layer's log is right about itself; only the timestamps reconcile them.
- **OSS ceiling for audit:** reading spend logs (`/spend/logs`) is OSS; spend reports (`/spend/report`) and the audit log of admin actions (who created, changed or deleted a key) are enterprise-only, and so is JWT auth, which would put a caller's identity rather than a shared key in each row (test 5).
- Operational, not LiteLLM: in run A the agent's request failed (503) because a new agent instance failed its startup probe within 30 s; runs D and C have the agent row.

- **Thinking condition held.** Claude's output tokens matched direct (45.4 mean through Bifrost, 46.4 direct, concurrency 1, non-streaming): Claude requests carry no `reasoning_effort`, so Bifrost added no thinking (it would turn on adaptive thinking if a caller sent one: `gateways/bifrost/NOTES.md`). Gemini's thinking count is "unknown" through Bifrost because it omits `reasoning_tokens` when Gemini doesn't think, as LiteLLM did; one Gemini request in 100 thought on each path.
- **Cold path not in these numbers.** The gateway's first (Gemini) pre-warm request took 13.7 s; a full cold start downloads the model catalog from getbifrost.ai (about 22 s of ~28 s; `gateways/bifrost/NOTES.md`).

### Test 2: routing and failover

**Run:** `scenarios scenarios/bifrost/failover.json`, 26 requests one at a time, a local run with the harness's virtual key on 2026-10-24: [`…092947Z…`](raw/bifrost/20261024T092947Z-scenarios-bifrost-failover-318543/), against `agw-bifrost` revision `00004`, the test window (`harness/scenarios/bifrost/README.md`): three model names aliased to ids that don't exist on the Agent Platform, so every call to them is a real upstream 404; two of them have routing rules (`governance.routing_rules`) that fail over to the other model, and the third (`test-gemini-broken-norule`) has none, for the no-fallback and caller-fallback cases. 26/26 matched.

| Case | What happened | What the caller sees |
| --- | --- | --- |
| Healthy Gemini (before and after) | 200 from Gemini (4/4) | no fallback info |
| Broken Gemini, with a rule | 200 from Claude (6/6, 3 streaming) | `model: claude-haiku-5-5`, `routing_info.is_fallback: true` |
| Broken Claude, with a rule | 200 from Gemini (5/5, 2 streaming) | `model: gemini-3.8-flash`, `is_fallback: true` |
| Broken, no rule, no fallbacks | 404 (2/2) | Vertex's own message |
| Broken, caller `fallbacks` | 200 from Claude (5/5, 2 streaming) | as with a rule |
| Healthy, caller `fallbacks` | 200 from Gemini (2/2) | fallback not used |
| Every fallback broken | 404 (2/2) | the primary's error |

Followed by hand checks of the same window (`gateways/bifrost/tests.ipynb`, "Test 2"). The committed config has no fallbacks or rules, so measured runs stay one model against itself.

- **Failover works both ways, streaming too, and the caller is told.** A broken Gemini model was answered by Claude, a broken Claude model by Gemini, in 0.5–3.7 s. The response's `model` names the model that answered, and `extra_fields.routing_info` adds `is_fallback: true` with the `primary_model`. Bifrost sends no headers for it (LiteLLM's was `x-litellm-attempted-fallbacks`).
- **Two ways to configure it, both OSS.** The operator attaches fallbacks to a rule (a CEL expression such as `model == "…"`); a caller can send its own `fallbacks: ["vertex/claude-haiku-5-5"]` with any request, with no config at all, which worked the same. A rule's fallbacks replace the caller's, and **a caller can't opt out of them**: `fallbacks: []` on a ruled model was still answered by Claude. LiteLLM let a caller opt out (`disable_fallbacks`).
- **Upstream errors pass through as they are.** With no fallbacks, the broken model's 404 reached the caller in about 65 ms with Vertex's own message, plus `extra_fields` naming the Bifrost key (`vertex-adc`) and the alias's real model id: a small information leak, noted for test 6. When every fallback fails too, the caller gets the **primary's** error; the fallback's own failure is only in Bifrost's routing log.
- **A fallback keeps the original request's parameters, and on Claude → Gemini that costs a lot.** A Claude request carries no `reasoning_effort` (Claude's condition is thinking off), so Gemini answering it thought at its default level. The notebook's saved check: 137 reasoning tokens, 174 of the 256-token cap, 2.37 s; the same question to Gemini through Bifrost with `reasoning_effort: "low"` used none (and in test 1 Gemini thought on 1 request in 100). Three earlier hand checks, not saved, gave 159–186 reasoning tokens, one leaving only 14 tokens of answer text. LiteLLM had the same carry-over (58 reasoning tokens). The other way, a Gemini request's `reasoning_effort: "low"` reaches Claude, where Bifrost turns it into adaptive thinking; Claude used none on these questions (55–63 output tokens against 51–63 asked directly, in unsaved hand checks; 42 in the notebook's), so it showed no cost here.
- **From Bifrost's source at the tested tag, not observable in these runs** (`gateways/bifrost/NOTES.md`): retries are off by default, so the first error goes straight to the fallback, and rules are evaluated once per request, so fallbacks can't loop.
- **OSS ceiling.** Nothing can force an error on a healthy model: Bifrost's mocker plugin is in the source but not compiled into the gateway (loading it needs a custom, dynamically linked build). So whether a 429 or a 500 fails over could only be shown with real upstream errors, here 404s; a real 429 wasn't produced. LiteLLM's mock switches covered both.
- **Closing the window left the rules running.** `source_of_truth: config.json` is documented to leave sections the file doesn't have untouched (its schema description); the committed file has no `routing_rules`, so both rules stayed active in Postgres after the redeploy (they matched only test names, which no key could use any more) until deleted through the admin API. It happened twice (after the run and after the notebook's window). Fixed afterwards: the committed file now declares `routing_rules`, `budgets` and `rate_limits` as empty lists, and an empty list does clear its section on a redeploy (a probe rule was gone after one, 2026-10-24; `harness/scenarios/bifrost/README.md`).
- **Not tested here:** failover through the agent, and a real 429 or 500 on a healthy model (no mocker in the build). With a rule on a real model name the gateway would decide the same way, but that is unverified.

### Test 3: cost control

**Runs:** seven `scenarios` runs on 2026-10-24, local, each through `harness/scenarios/bifrost/run-cost.sh` with a throwaway virtual key made through the admin API for the run and deleted after it (limits in each run's `NOTE.md`, the key's own quota afterwards in `quota.json`): [rpm](raw/bifrost/20261024T101746Z-scenarios-bifrost-cost-rpm-beba9b/), [tpm](raw/bifrost/20261024T101931Z-scenarios-bifrost-cost-tpm-3d12b5/), [budget](raw/bifrost/20261024T102102Z-scenarios-bifrost-cost-budget-6a1059/), [race](raw/bifrost/20261024T102115Z-scenarios-bifrost-cost-race-75be3b/), [model budget](raw/bifrost/20261024T102132Z-scenarios-bifrost-cost-model-budget-d10e33/), [reset](raw/bifrost/20261024T102157Z-scenarios-bifrost-cost-reset-0a2109/), all on revision `00010` (committed config), and [unpriced](raw/bifrost/20261024T103315Z-scenarios-bifrost-cost-unpriced-6e86dd/) on a test window (revision `00011`). Repeated by hand in `gateways/bifrost/tests.ipynb` ("Test 3"), each cell with its own throwaway key.

| Run | The key's limit | What happened |
| --- | --- | --- |
| rpm | 3 requests a minute | 3 answered, then 429 in ~13 ms with no model call; answered again after 70 s |
| tpm | 1000 tokens a minute | one at a time, 10 answered and the 11th refused; 12 at once all admitted (1,230 tokens), then refused |
| budget | $0.0002 an hour | 7 answered (the 7th crossed it), then 402 for both models |
| race | $0.0001 an hour (~3 requests) | 10 at once all answered: $0.000315, 3.1× the budget; the next 10 refused |
| model budget | $0.0003 an hour, Gemini only | 2 Gemini answered, then 402; Claude kept answering |
| reset | $0.0001 a minute | refused, then answered again 75 s later |
| unpriced | $0.0001 an hour, an alias with no price of its own | charged anyway, at Claude's price: 3 answered, then 402 |

- **Every limit is hard, refused before the model is called, and OSS.** A rate limit gives 429 and a budget 402 (LiteLLM: 429 for both), in about 13 ms, with nothing spent. The messages name the limit, not the key ("request limit exceeded (3/3, resets every 1m)"), unlike LiteLLM's, which named the key alias and hash. Budgets refuse the next request for either model, and a budget on one model refuses only that model.
- **Bifrost checks without reserving, so bursts overshoot.** Each request is admitted if usage so far is under the limit, and charged asynchronously after it answers. One at a time, the request that crosses a limit is admitted and the next refused. At once, every request that starts below the limit is admitted: ten requests against a budget of three spent 3.1× the budget, twelve against a token limit of ten used 1.23×, and five in the notebook spent 3.4× a smaller budget. LiteLLM is the opposite: it reserves each request's worst case first, so a burst is refused early and never overshoots by more than one request. With Bifrost, a budget's real ceiling is the limit plus one burst.
- **Per-model budgets are OSS here.** A budget on Gemini only, under one key, worked as expected. In LiteLLM the same thing (`model_max_budget`) is enterprise-only (its test 3). Keys also take several budgets with different windows, per-provider limits and an expiry.
- **The price is right, and Bifrost adds no uplift.** In the notebook a fresh key's charge for one Gemini and one Claude request equalled tokens × the config's EU prices exactly (ratio 1.000), once the quota caught up. Without those overrides Bifrost would charge the live datasheet's prices: Gemini at 45% of its real EU price, Claude at the global price (`gateways/bifrost/NOTES.md`).
- **An alias can't be used to make an unpriced model.** The window aliased `test-claude-unpriced` to Claude with a `model_name` that has no price, expecting Bifrost to charge nothing (its source charges a budget only when cost > 0). It charged the alias at exactly Claude's override price instead: pricing follows the model an alias resolves to. Whether a model the catalog doesn't know is free for budgets remains a source-level reading, untested.
- **Callers can see their own budget, late.** No quota headers on responses (LiteLLM sent none either). A key's holder can read its budgets and limits at `GET /api/governance/virtual-keys/quota`, but that view lags the counters Bifrost enforces by about 10 s, for spend and request counts alike: in the notebook it showed nothing for 8 s after a request, then the exact cost and a count of 1 at 10 s (the budget run's `quota.json`, read 3 s after its last request, showed $0.000113 against about $0.00022 enforced). The 402 message rounds to four decimals ("0.0002 >= 0.0001 dollars" for a $0.00005 budget), which misreports small budgets.
- **Resets are on time.** A one-minute budget let a request through 75 s after it was spent (resets are swept every 10 s).
- **Keys made through the admin API don't survive a restart.** `virtual_keys` is declared in `config.json`, the source of truth, so a deploy removes any other key (a probe key minted before the window's deploy was gone after). Good for throwaway keys; it also means keys made in the UI disappear at the next deploy.
- **OSS ceiling:** nothing in this test needed a licence. There is no LiteLLM-style throttle mode (an exhausted budget becoming a reduced rate); a budget override (`override_amount`) raises a limit for a while instead.

### Test 4: inline screening

**Runs:** `scenarios harness/scenarios/bifrost/screening.json` on 2026-10-24, local, with the harness's virtual key: the shared case set (`harness/scenarios/screening-cases.json`, 18 synthetic cases) on both models, once each, 36 requests per run. **A** [`…111043Z…`](raw/bifrost/20261024T111043Z-scenarios-bifrost-screening-c2c74c/), committed config (revision `00012`); **B** [`…111453Z…`](raw/bifrost/20261024T111453Z-scenarios-bifrost-screening-d6d09e/), a guardrail window (`00013`): `guardrails_config` with Bifrost's documented `regex` redaction example (email, US SSN, card numbers) attached to a rule for every input and output. Both runs matched 36/36 (no expectations beyond an answer). Repeated by hand in `gateways/bifrost/tests.ipynb` ("Test 4").

| Group (cases × 2 models) | A: committed config | B: guardrail configured | LiteLLM A (no guardrails) |
| --- | --- | --- | --- |
| PII in the prompt (6) | 12 leaked | 12 leaked | 11 leaked, 1 withheld |
| Prompt injection (6) | 12 passed, no canary returned | 12 passed, no canary returned | 12 passed, no canary returned |
| PII in the answer (2) | 3 withheld, 1 leaked | 3 withheld, 1 error (empty answer) | 2 withheld, 1 leaked, 1 error |
| Benign near-misses (4) | 8 passed | 8 passed | 8 passed |

- **Bifrost OSS doesn't screen anything.** Every PII value in a prompt reached the model and came back in the answer; nothing was blocked or masked; no built-in OSS plugin inspects message content. The models did the work they did through LiteLLM: neither obeyed any injection (no canary came back; answers refuse or answer the harmless part) and both repeated PII. The results match LiteLLM's run A group for group, within a case or two of model-side variation.
- **A configured guardrail is accepted and ignored, silently.** `guardrails_config` is in Bifrost's config schema, so the window validated and the revision started, but no OSS code reads it: no log line on the revision mentioned guardrails, and run B was identical to run A. An operator who follows Bifrost's guardrail docs on the OSS image gets no error, no warning and no screening. It's the same failure mode as LiteLLM's audit log (silently empty), and the opposite of LiteLLM's guardrails, whose built-in kinds were OSS (its test 4).
- **"Blocked, logged or invisible": logged.** Bifrost stores each request's content by default (`disable_content_logging: false`): the `pii-email` prompt and answer sat in its Postgres logs store (`input_history`, `output_message`, `content_summary`; read as flags only). Unlike LiteLLM's `store_prompts_in_spend_logs`, the record held no ID token, virtual key or Cloud Run auth header (`logging_headers` is unset). So PII sent through Bifrost isn't screened, but it is kept, for 365 days by default (`log retention days: 365` at startup).
- **OSS ceiling:** guardrails, PII redaction, secrets detection and prompt guards are enterprise-only (the OSS UI shows "contact us" pages, and the config is ignored). The OSS route to any screening is a custom `.so` plugin, which needs a rebuilt, dynamically linked Bifrost. LiteLLM's content filter and LLM judge needed no licence.

### Test 5: identity and secrets

**Run:** `scenarios harness/scenarios/bifrost/auth.json` via `run-auth.sh`, 2026-10-24, local, revision `00014` (committed config): [`…135211Z…`](raw/bifrost/20261024T135211Z-scenarios-bifrost-auth-2d6094/), 13/14 cases as expected, 4 of them reaching a model, with throwaway keys made through the admin API (Claude-only, expired, inactive, deleted, rotated) and the agent's own key. Repeated by hand in `gateways/bifrost/tests.ipynb` ("Test 5"), plus the `x-bf-vk` and direct-key cases the harness can't send, and read-only `gcloud` checks of where the credentials are.

**Gateway → model: workload identity, and nothing else is possible here.** Bifrost calls the Agent Platform as its Cloud Run service account (`agw-gw-bifrost`) through Application Default Credentials (the Vertex key in `config.json` has empty `auth_credentials`). The account has no user-managed keys, and the project's org policy blocks creating any (`iam.disableServiceAccountKeyCreation`), as in Phase 1.

**Caller → gateway: two layers, refusing differently.**

| Credential | Status | Who refused | Message |
| --- | --- | --- | --- |
| none | 403 | Cloud Run (HTML) | Forbidden |
| a key, no ID token | 401 | Cloud Run (HTML) | Unauthorized |
| an ID token, no key (or a value without `sk-bf-`, or a direct provider key) | 401 | Bifrost | "virtual key is required" |
| an unknown, deleted or rotated-away key | 401 | Bifrost | "access not found. The provided credential does not exist or has been revoked." |
| an expired key / an inactive key | 403 | Bifrost | "virtual key has expired" / "virtual key is inactive" |
| a Claude-only key asking for `vertex/gemini-3.8-flash` | 403 | Bifrost | "Model 'gemini-3.8-flash' is not allowed for virtual key '<name>'" |
| the same key asking for `gemini-3.8-flash` (bare name) | 400 | Bifrost | "could not auto resolve a provider for the request" |
| a valid key, the agent's key from another identity, the rotated key's new value | 200 | | |

- **IAM keeps the gateway off the internet; the key is the identity inside it.** As with LiteLLM, anything without an invoker's ID token is refused by Cloud Run before Bifrost sees it, and past that Bifrost knows a caller only by its key: the agent's key worked when sent with a user's ID token (the local scenario run and the notebook both ran as a user, not as `agw-agent`). A key is a bearer secret. Binding it to a Google identity (SSO, users, RBAC) is enterprise-only; the OSS route would be a custom pre-auth plugin (`HTTPTransportPreAuthHook`), which needs a rebuilt Bifrost.
- **Key states are OSS and enforced at once**, including **rotation**, which LiteLLM gated (its `/key/regenerate` returned 500 without a licence): the rotated key's old value was refused straight away (no `vk_rotation_cooldown` configured) and the new one worked. An unknown, a deleted and a rotated-away key get the same message, so a caller can't tell them apart.
- **Error bodies give nothing away about keys.** No refusal echoed any part of a key (LiteLLM's 401 for an unknown key echoed its last four characters and its SHA-256 hash). The model-restriction 403 names the key's *name*, not its value.
- **A model restriction can look like a routing error.** With a bare model name, Bifrost picks the provider from the key's own allowed models, so a Claude-only key asking for Gemini fails provider resolution (400, "could not auto resolve a provider") before the model check; only `vertex/gemini-3.8-flash` gets the clear 403. A caller debugging the 400 would look in the wrong place.
- **`x-bf-vk` takes any value as a key**, without the `sk-bf-` prefix check `Authorization` applies; a wrong one still gets 401. A direct provider key (`x-bf-direct-key: true`) is refused because the config sets `allow_direct_keys: false`, but the refusal says "virtual key is required", not that direct keys are off.
- **A virtual key can't use the admin API** (401 on `/api/governance/virtual-keys`), except its own read-only quota view (200).
- **The gateway's own secrets are all in Secret Manager.** Admin password, setup token, encryption key (which encrypts stored keys; lookups use a SHA-256 hash), database password and both caller keys reach the container as secret references; the plain environment holds only the project, the database host, user and name, and the admin username. Each caller's key secret is readable only by that caller's service account. Open at the time of the test: every gateway service account (`agw-gw-litellm`, `agw-gw-kong` included) could read every `agw-*` secret through a project-level conditional binding, so Bifrost's admin password was readable by accounts nothing ran as. Closed at Phase 3 start: each gateway now reads only `agw-<gw>-*`.
- **Caller credentials don't travel upstream.** Bifrost forwards caller headers to the provider only from an allowlist (none configured), so the caller's ID token stays at the gateway (source; not observable upstream).

### Test 6: audit fidelity

**Runs:** `run-audit.sh` on 2026-10-24, local: `harness/scenarios/bifrost/audit.json` (four requests a cooperating caller puts in one session with `x-bf-session-id` and tags with its own `x-bf-lh-*` log headers, one of them refused, plus one untagged) and one request through `agw-agent` as it is, then `harness/scenarios/bifrost/audit_trail.py` collects the trail they left (Bifrost's logs store through the admin API; Cloud Run request and container logs of the gateway and the agent) and joins it. **A** [`…141029Z…`](raw/bifrost/20261024T141029Z-scenarios-bifrost-audit-fcb2f6/), committed config; **B** [`…141605Z…`](raw/bifrost/20261024T141605Z-scenarios-bifrost-audit-fcf408/), a window with `logging_headers: ["X-Serverless-Authorization", "Authorization"]`. Each run's `trail.md` is the evidence (values redacted, content reduced to flags). The harness gained a per-case `headers` field to send Bifrost's join keys, and the generic parts of LiteLLM's collector moved into `agw_harness/trail.py`.

| What an auditor asks | Where it is | A (default) | B (headers logged) |
| --- | --- | --- | --- |
| Which caller (key) | log row `virtual_key_name` (and id) | ✓ | ✓ |
| Which Google identity | nowhere by default: Cloud Run request logs don't name the caller | ✗ | ✗ (but its ID token is stored) |
| When, which model, provider key, tokens, cost, latency, outcome | log row, one per request that reached a provider | ✓ | ✓ |
| A refused request | governance refusals (403 model not allowed, 429 rate limit) have a row with `status: error`; a 400 at provider resolution has none (Cloud Run's request log only) | partly | partly |
| The gateway request it came from | the `x-request-id` Bifrost returns is the row's id; Cloud Run's request log joins by time only (no trace in the row) | ✓ (by the returned id) | ✓ |
| The agent run it belongs to | nothing shared: the agent sends no session, tag or request id | key and time only | key and time only |
| Grouped by the caller's own session and tags | row `session_id`, `metadata` (`x-bf-lh-*`) | ✓ | ✓ |
| What was said | row `input_history`, `output_message` | ✓ (by default) | ✓ |
| Who created or deleted a key | admin audit log | ✗ enterprise-only | |

- **Every request that reached a provider has a row, and the caller can find it.** The row holds the virtual key's name and id, provider, model, the provider key used, tokens, cost, latency, Bifrost's own overhead, status, session, the caller's user agent and its own tags. Bifrost returns `x-request-id` on every response, and that id **is** the row's id, so a caller who keeps it can point at the exact record without cooperating in advance (LiteLLM needed its `x-litellm-call-id` header; a caller can also send its own `x-request-id`).
- **Some refusals leave no row.** The recorded run's refused request (a 400 at provider resolution, an unknown model) is only in Cloud Run's request log; Bifrost's logs store, which is what its UI shows, has nothing. Governance refusals do leave a row: in the notebook a 403 (model not allowed) and a 429 (rate limit) each had one, with `status: error` and the content stored. LiteLLM's spend log recorded every refusal it made.
- **The agent hop doesn't join, as with LiteLLM.** The agent's gateway call is found only by its key name (`agw-agent`) and time; its user agent is the OpenAI client's (`AsyncOpenAI/Python`), and nothing in the row names the agent's session or trace. In run A it arrived 39 s after the agent's `/run`, on the agent's cold start.
- **No log names a Google identity.** Neither Bifrost's rows nor Cloud Run's request logs say which invoker called; the key name is the only caller identity.
- **Content is stored by default, credentials aren't.** Prompts and answers are kept in Postgres (365-day retention, `disable_content_logging: false`); by default no header is, so no ID token or key value is in any row. That is safer than LiteLLM, whose `store_prompts_in_spend_logs` stored ID tokens along with prompts.
- **But an operator can store credentials with one setting.** With `logging_headers` naming `X-Serverless-Authorization` and `Authorization` (run B), every row kept the caller's ID token and its virtual key in its metadata, the agent's included. The ID tokens expire within the hour; the virtual keys don't, and stay in Postgres for the retention period. Callers can also put anything they like in the rows through `x-bf-lh-*` headers.
- **OSS ceiling:** the admin audit log (who changed keys, budgets or config) is enterprise-only, as are log export to BigQuery, Pub/Sub, Kafka and Datadog (configured, those plugins are skipped silently). The request log itself, its UI and its API are OSS.

### Test 3: cost control

**Runs:** four `scenarios` runs on 2026-10-31, local, each through `harness/scenarios/kong/run-cost.sh` with a throwaway consumer made through the Admin API for the run (an ACL group, a one-hour key and its limit, all tagged `agw-throwaway`, so decK ignores them) and deleted after it: [rpm](raw/kong/20261031T183502Z-scenarios-kong-cost-rpm-7ebac2/), [race](raw/kong/20261031T183701Z-scenarios-kong-cost-race-1a7891/), [model limit](raw/kong/20261031T183801Z-scenarios-kong-cost-model-limit-0712ab/) and [caps](raw/kong/20261031T190201Z-scenarios-kong-cost-caps-d23b18/) (a re-run: the first gave Claude the harness's two-sentence instruction, so it showed nothing about the cap). - **Kong OSS limits requests, not tokens or money.** `rate-limiting` counts requests per consumer (or per consumer and route) in fixed clock windows from a second to a year, and refuses with 429 `API rate limit exceeded` before any model call (11–19 ms one at a time). Limits on tokens or cost are `ai-rate-limiting-advanced`, which is enterprise, so OSS has no budget of any kind. LiteLLM and Bifrost both had hard budgets and token limits in OSS.
- **Callers can see their limit.** Every response on a limited route carries `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` (seconds to the end of the window) and `X-RateLimit-*-Minute`, and a 429 adds `Retry-After`. Neither LiteLLM nor Bifrost sent quota headers (LiteLLM's rate-limit 429s carried only `retry-after: 60`). The message names neither the limit nor the consumer.
- **A burst can get through a limit.** Kong checks the count when a request arrives and adds to it afterwards in a zero-delay timer (`rate-limiting/handler.lua`: `timer_at(0, increment, …)`), with no reservation. In the notebook, 9 of 10 requests sent at once were admitted against a limit of 3. In the run the limit held at exactly 3, but all three admitted requests carried `RateLimit-Remaining: 2`, so each was checked against a count of 0: it held because the timers ran before the fourth check, not by design. Why the two differ is untested: both opened about ten connections at once (the run's ten requests started within 30 ms), so it comes down to how arrivals and the increment timers interleaved inside Kong. Like Bifrost, a limit's real ceiling is the limit plus one burst; LiteLLM reserved and never overshot by more than one.
- **A per-model limit is OSS, as a request count.** A `rate-limiting` plugin on a consumer and a route limits that consumer on that model only; the other model's routes carry no rate-limit headers at all. Bifrost's per-model budgets were OSS too; LiteLLM's are enterprise.
- **The only token control is the route's per-request cap, on the translated route.** On the Gemini route `kong.yaml`'s `max_tokens: 256` overrides whatever the caller sends (`max_tokens` or `max_completion_tokens`; `merge_config_defaults` in `kong/llm/drivers/shared.lua`), and Gemini counts its thinking inside it: at its default level (Kong drops `reasoning_effort`, test 1) the notebook's two answers used 242 and 244 thinking tokens and showed 10 and 8, stopping at `max_tokens` mid-sentence. Claude's native route doesn't touch the body, so a caller sets its own cap, up to the model's.
- **Kong's logged cost leaves out thinking.** Kong prices each Gemini request from `kong.yaml` (`input_cost` 1.65, `output_cost` 8.25 $ per million tokens) and logs it in the `file-log` row's `ai` field, but it counts only the visible output: the notebook's two caps requests were logged at $0.00015 and $0.00013, where tokens as Vertex bills them (38 in, 252 out, thinking included) come to about $0.0021 each, 15–17× more. Claude, on its pass-through route, is logged with no tokens or cost. The cost is logged only: nothing reads it.
- **Counters are in memory.** The default `local` policy counts in a shared dictionary that all of an instance's nginx workers use: one count per instance, which is the whole count here (max 1 instance), but each Cloud Run instance would count separately with more, and a restart forgets every count. OSS also has `cluster` (counts in Postgres) and `redis` policies; not tested.
- **OSS ceiling:** limits on tokens or cost (`ai-rate-limiting-advanced`) and sliding windows (`rate-limiting-advanced`) are enterprise; not tried. With OSS only, spend is bounded per request by the route caps and only nominally per minute by request counts, which bursts overshoot and restarts reset: for Gemini, about (the limit + one burst) × 256 output tokens a window, plus whatever input callers send; for Claude, whatever its callers ask for.

- **`ai-prompt-guard` is a regex deny list, and it blocks fast and quietly.** It matches the user's messages only (all roles with `match_all_roles`), at most 10 patterns, and refuses with a 400 `{"error":{"message":"bad request"}}` before any model call, deliberately not saying why (`guard-prompt.lua`: "don't let users know 'ai-prompt-guard' is in use"). That's the opposite of LiteLLM's content filter, whose 400 named the rule that fired. It never sees the answer, so output PII got through, and it can't mask, only refuse. **The 22 of 22 is a best case:** the patterns were written knowing the case set; a deny list is as good as its patterns, and the base64 injection shows what it can't read. Ten patterns had to cover six PII shapes and four injection families; LiteLLM's content filter came with prebuilt patterns for some PII shapes.
- **`ai-request-transformer` masks, but breaks the translated Gemini route.** On Claude's pass-through route the LLM's rewrite is what Vertex receives, and all six PII values arrived as `[REDACTED]`. On the translated Gemini route Kong skips translating the response once a transformer has run (`normalize-json-response.lua:72`), so the caller gets Vertex's native `generateContent` JSON (`candidates`, `usageMetadata`) in reply to an OpenAI request: 18 of 18 errors, with HTTP 200. All were non-streaming; streamed chunks go through a different filter (`normalize-sse-chunk.lua`) with no such check, so streaming may differ (not tested). From the source the masked body should have reached Gemini (the transformer replaces nginx's request body, which `ai-proxy` then reads and translates; the run can't show it, with the answer unread and payloads not logged), but no OpenAI client can read the answer. It screens only personal data in the request: injections and output PII pass. Every request pays a second model call (+2–4 s at the median; the rewrite alone took 6 s on the base64 case), and one Claude answer (`inj-base64`) came back as a 200 with nothing the harness could read as text (Kong's log shows a normal-sized response) after the run's longest rewrite; what the rewrite changed isn't logged (payloads off). Unexplained.
- **"Blocked, logged or invisible": blocked, and logged without a reason.** A guard refusal is an ordinary `file-log` row: status 400, the consumer and route, zero tokens, no pattern named and no content (`log_payloads: false`; the guard logs its reason at debug level only). The transformer's call is logged with its tokens and cost under `ai.ai-request-transformer`, but the answer's own usage and cost are lost: the same early return in `normalize-json-response.lua` skips the cost calculation and the `X-Kong-LLM-Model` header (absent on all 36 run C responses), and the Gemini row's `ai.proxy.usage` repeats the transformer's numbers. With payload logging off, Kong keeps no prompt or answer, unlike Bifrost, which stores content by default.
- **Scope, from the schemas (not tested):** `ai-prompt-guard` can be attached to a consumer, so per-caller screening is OSS (LiteLLM's per-key guardrails are enterprise); `ai-request-transformer` can't (`no_consumer`). `ai-response-transformer`, which would be the place to mask answers, was not tried: it runs after `ai-proxy` and makes the upstream call itself (`transform-response.lua`, `subrequest`), forwarding all the caller's remaining request headers (the Kong key is already gone with our `hide_credentials`), then sends the answer to its own LLM: a second model call per request, and a second copy of the answer in another model.
- **OSS ceiling:** PII detection and redaction (`ai-sanitizer`), semantic prompt guards (`ai-semantic-prompt-guard`) and the hosted guardrail integrations (`ai-gcp-model-armor`, `ai-azure-content-safety` and others) are enterprise; not tried. With OSS only, screening is a hand-written regex deny list or a home-made LLM rewrite on untranslated routes only; neither looks at the answer.

### Test 5: identity and secrets

**Runs:** `scenarios harness/scenarios/kong/auth.json` via `run-auth.sh`, 2026-11-01, local, revision `00003` (committed config, `make diff-kong` 0/0/0): [`…184431Z…`](raw/kong/20261101T184431Z-scenarios-kong-auth-3b8006/), 13/13 cases as expected, 4 of them reaching a model (Claude), with six throwaway consumers made through the Admin API (valid, Claude-only, no group, expired, deleted, rotated; tagged `agw-throwaway`, deleted on exit) and the agent's own key. The expired, deleted and rotated-away keys were each used once while valid, so the run also shows a lapsed key leaving Kong's cache. Kong's log rows are in the run's `kong-log.json`. Plus an **echo window** [`…184742Z…`](raw/kong/20261101T184742Z-echo-upstream-headers/) (no model call): copies of the Claude and Gemini routes pointed at a loopback sink inside Kong that answered with the names of the headers it received, and the segment lengths of the ID token. It shows what Kong sends upstream through the same plugins and proxy settings; what reaches Vertex itself differs only in `Host` and path, by the source (not observed at Vertex). Repeated by hand in `gateways/kong/tests.ipynb` ("Test 5"), plus the cases the harness can't send (a key without `Bearer `, a made-up key in the query string, a caller's key on `/admin-api`), rotation with both keys live, and read-only `gcloud` checks of where the credentials are.

**Gateway → model: workload identity, and nothing else is possible here.** Kong calls the Agent Platform as its Cloud Run service account (`agw-gw-kong`), with a token from the metadata server (`gcp_use_service_account: true`; `lua-resty-gcp`). The account has no user-managed keys (notebook); the project's org policy against creating any was checked in Phase 1 and carried over.

**Caller → gateway: two layers, refusing differently.**

| Credential | Status | Who refused | Message |
| --- | --- | --- | --- |
| none | 403 | Cloud Run (HTML) | Forbidden |
| a key, no ID token | 401 | Cloud Run (HTML) | Unauthorized (`WWW-Authenticate: Bearer error="invalid_token"`) |
| an ID token, no key (or a made-up key in the query string) | 401 | Kong `key-auth` | "No API key found in request" |
| an unknown, expired, deleted or rotated-away key (or a real key without `Bearer `) | 401 | Kong `key-auth` | "Unauthorized" (`WWW-Authenticate: Key`) |
| a valid key whose consumer is in no allowed group, or a caller's key on `/admin-api` | 403 | Kong `acl` | "You cannot consume this service" |
| a Claude-only key asking for Gemini | 403 | Kong `request-termination` scoped to the consumer and the `gemini` service | the plugin's own message |
| a valid key, the Claude-only key on Claude, the agent's key from another identity, the rotated key's new value | 200 | | |

- **IAM keeps the gateway off the internet; the key is the identity inside it,** as on LiteLLM and Bifrost. Past Cloud Run, Kong knows a caller only by its key: the agent's key worked from a user's ID token. Binding the consumer to the caller's Google identity is `openid-connect`, which is enterprise. The OSS `jwt` plugin checks tokens against keys configured per consumer, not Google's published ones (not tried), and Kong can't verify the ID token it receives: Cloud Run replaces its signature (`gateways/kong/NOTES.md`). It doesn't need to, since Cloud Run already verified it and rejects a forged one, so an OSS `pre-function` could map the token's `email` claim to a consumer or check it against the key's consumer: plain config on Kong, where Bifrost needed a custom build (not tried).
- **Key states are few, and enforced at once (one instance).** A Kong OSS key exists or doesn't, with an optional `ttl`: an expired, a deleted and a rotated-away key all got the same 401 within seconds, though Kong had each one cached (deleting a credential invalidates its cache entry on the instance that handled the delete, and others learn of it within `db_update_frequency`, 5 s; a `ttl` caps the cache entry's lifetime). There is no "inactive" key and no per-key model list: the nearest are a consumer outside the allowed ACL groups (403) and a `request-termination` plugin scoped to a consumer and a service, both OSS. Rotation is by hand, as on LiteLLM OSS: add a second key to the consumer, then delete the first, with both accepted in between (notebook, on `/admin-api`). LiteLLM's regenerate endpoint is enterprise; Bifrost has a built-in rotate operation in OSS.
- **Error bodies give nothing away about keys,** like Bifrost's: no refusal echoed any part of a key, and an unknown, expired and deleted key can't be told apart. A `key-auth` refusal (no key, or an unknown, expired, deleted or rotated-away one) is logged with no consumer, so a failed attempt can't be traced to the key's owner (test 6); the `acl` and `request-termination` 403s do name the consumer.
- **Kong forwards the caller's headers to the model.** The echo window got 23 header names on both routes: `Authorization` was Kong's own Google access token (`ai-proxy` overwrites the header the Kong key came in; `hide_credentials` also strips it, which matters on routes without `ai-proxy`), but the caller's `X-Serverless-Authorization` went upstream with segment lengths 102.426.27, i.e. a full header and claims section (for a Google ID token: the caller's e-mail, audience, issuer; contents not recorded) and Cloud Run's 27-character placeholder signature, along with any custom header the caller sent, the client's address (`X-Forwarded-For`, `X-Real-IP`, `Forwarded`) and Kong's `X-Consumer-Id`, `X-Consumer-Username` and `X-Credential-Identifier`. The token can't be replayed, and here the upstream is Google, which issued it and saw it at Cloud Run; but the caller's address, custom headers and Kong consumer names reach the model provider, and with a third-party upstream so would the caller's identity. Bifrost forwards only allowlisted headers (none configured). On Kong a `request-transformer` on the chat services could remove ordinary headers such as `X-Serverless-Authorization`, custom ones and `X-Consumer-*` (OSS; not tried), but not `X-Forwarded-*` and `X-Real-IP`, which Kong's nginx template sets itself (`nginx_kong.lua`, `proxy_set_header`).
- **Kong stores caller keys in clear.** `key-auth` keeps each key as given (here the literal `Bearer <key>`) in Postgres, and the Admin API returns it; encrypted keys (`key-auth-enc`) are enterprise. LiteLLM stores virtual-key hashes; Bifrost encrypts stored keys and looks them up by hash. The caller keys reach Kong from Secret Manager by decK at sync time (`make sync-kong`), not through the container: the admin key and database password are the only secret environment variables, and the bootstrap file, start script and database CA are secret volumes; everything else in the environment is plain configuration (names checked in the notebook). Each caller's key secret has a secret-level grant to that caller's service account, but foundation's per-gateway prefix grant (`iam.tf`, every `agw-kong-*` secret) also lets `agw-gw-kong` read both caller keys, which Kong never needs: decK writes them.
- **OSS ceiling:** identity-bound callers (`openid-connect`, `jwt-signer`), encrypted keys (`key-auth-enc`), secret references to GCP Secret Manager (vaults other than `env`), RBAC for the Admin API and workspaces are enterprise; not tried. With OSS only, a caller is a bearer key stored in clear, scoped by ACL groups, unless a `pre-function` ties it to the Cloud Run identity (above; not tried).

- **Every request that reaches Kong has a row, refusals included, and the caller can find it.** Kong's `file-log` writes one JSON line per request, whatever its outcome: both refusals here had rows, as did test 5's 401s and 403s (a request Cloud Run refuses never reaches Kong and is only in Cloud Run's log) (Bifrost left none for a refusal at provider resolution; LiteLLM's spend log recorded every refusal). The `X-Kong-Request-Id` Kong returns is the row's id, as Bifrost's `x-request-id` is. The 404, refused before routing and authentication, is logged with no route, service or consumer: only the caller's own tag and user agent say whose it was.
- **The join to Cloud Run is exact.** The row keeps every request header, including the `X-Cloud-Trace-Context` Cloud Run added, so each row joins Cloud Run's request-log entry by trace id; Bifrost's rows joined by time only. (Kong's serializer reads up to 100 request headers, `pdk/log.lua`; these runs sent about 15.) The same header-keeping makes a caller's own tags (`x-agw-session`, `x-agw-case`) searchable with no gateway feature (Bifrost needed its `x-bf-lh-*` prefix and session header).
- **The agent hop doesn't join, as on LiteLLM and Bifrost.** The agent's call is one row by consumer `agent` and time (user agent `AsyncAnthropicVertex/Python`); its `traceparent` is a new trace, not the agent's `/run`, so nothing in the row names the agent's session or trace.
- **No log names a Google identity, by our choice.** The consumer is the only caller identity in these runs, as on the other two. But the ID token reaches Kong with its claims readable (Cloud Run replaces only the signature, test 5), and our `kong.yaml` overwrites it in the log; a `custom_fields_by_lua` that logged just the decoded `email` claim would put a Google identity on every row without storing a token (OSS; not tried).
- **Content is off by default, and partial when on.** With `log_payloads: false` (our config) no prompt or answer is kept. With it on (run B), every row through `ai-proxy` holds the request body (as sent upstream; for the refused 400, as received, since nothing was sent), the agent's included, and the answer for the requests that got one, except a streamed Claude answer (a `preserve` stream's body isn't collected); they sit in Cloud Logging for its retention (30 days), not in a store of Kong's. Bifrost stores content by default.
- **Credentials don't reach the rows.** Kong's serializer always redacts `Authorization` (`pdk/log.lua`), whatever it holds: on model rows Kong's own Google token (the caller's key was already removed by `hide_credentials`), and on the 404, where `key-auth` never ran, the caller's key. So our keys are kept out by Kong's default. The ID token is kept out by config: `kong.yaml` overwrites `X-Serverless-Authorization`, and by default Kong would log it in every row, with its signature replaced by Cloud Run (not replayable) but its claims, the caller's identity, readable (NOTES). No row in either run held an ID token or Google token (scanned), and every `Authorization` was removed or `REDACTED`. LiteLLM's `store_prompts_in_spend_logs` and Bifrost's `logging_headers` store usable credentials, but only when switched on.
- **Admin changes are only request rows.** Kong OSS has no admin audit log. Changes made through the `/admin-api` route leave ordinary rows: consumer `admin`, method, path (the DELETE named the consumer; the POST didn't say what it created), time and user agent, but no body. Kong Manager writes through the `/manager-api` route, so its changes get rows too, but under consumer `manager`, the one shared login, not a person. The Admin API's own port (`127.0.0.1:8001`, reachable only inside the container) leaves only Kong's admin access-log line on stdout (method and path, no consumer; decK goes through the route here, so it gets rows), and writes to Postgres directly, including the bootstrap import at each start (`start.sh`, `kong config db_import`), leave nothing of Kong's.
- **Export is mostly OSS.** The bundled exporters (`file-log`, `http-log`, `opentelemetry`, `datadog`, `syslog`, `tcp`/`udp`-log, `statsd`, `loggly`) are OSS (not tried beyond `file-log`); Kafka export is enterprise, absent from the OSS source. Bifrost's BigQuery, Pub/Sub, Kafka and Datadog exporters are enterprise (its OTel plugin is OSS).
- **OSS ceiling:** the admin audit log (who changed what, with the change) is enterprise, and analytics are Konnect's (paid); not tried. With OSS only, the request trail is complete and joinable; caller identity is the consumer unless a custom log field adds the ID token's email claim (not tried), and admin changes are request lines.

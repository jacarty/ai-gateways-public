Test 5, what Kong forwards upstream (2026-11-01, about 18:47 UTC), run locally from the devbox with a one-off script (not the harness; its output is `echo.json`). Gateway: `agw-kong` revision `00003-7g6` (Kong OSS 3.9.3), in a `TEST ONLY` echo window synced by decK (7 created; closed straight after: 7 deleted, then `make diff-kong` 0/0/0): a `claude-echo` route (`ai-proxy` `preserve`, as the Claude routes) and a `gemini-echo` route (`ai-proxy` `llm/v1/chat`, as the Gemini route), each with `upstream_url` pointed at `http://127.0.0.1:8080`, and an `echo-sink` route matching only `Host: 127.0.0.1` whose `pre-function` answered, before any auth plugin, with the names of the headers that reached it, the kind of `Authorization` and the segment lengths of `X-Serverless-Authorization`, never a value. So it shows what Kong sends upstream through the same plugins and proxy settings (on the real routes, to Vertex, with a different `Host` and path; Vertex itself not observed); no model was called. One request per route from a throwaway consumer (`agw-t5-echo-*`, `callers`, 10-minute key, deleted after), sending the ID token, the Kong key and an extra `X-Agw-Probe` header.

Both routes forwarded the same 23 headers: `accept-encoding, authorization, connection, content-length, content-type, forwarded, host, traceparent, user-agent, via, x-agw-probe, x-cloud-trace-context, x-consumer-id, x-consumer-username, x-credential-identifier, x-forwarded-for, x-forwarded-host, x-forwarded-path, x-forwarded-port, x-forwarded-proto, x-kong-request-id, x-real-ip, x-serverless-authorization`.

- `Authorization` held a Google access token (Kong's service account, from `ai-proxy`, which overwrites the header the Kong key came in; `hide_credentials` strips the key too, so this run can't tell the two apart).
- `X-Serverless-Authorization`, the caller's ID token, went upstream with segment lengths 102.426.27: a full header and claims section (for a Google ID token, the caller's identity: e-mail, audience, issuer; contents not recorded) and its signature replaced by Cloud Run's 27-character placeholder, so it can't be replayed; the upstream here is Google, which issued it, but a third-party upstream would get the caller's identity.
- Any other caller header goes too (`X-Agw-Probe`), with the client's address (`X-Forwarded-For`, `X-Real-IP`, `Forwarded`) and Kong's own `X-Consumer-Id`, `X-Consumer-Username` and `X-Credential-Identifier` (the credential's id, not the key).
- The Gemini route sent the path from `upstream_url` (`/agw-echo-sink/gemini`); the Claude route sent the client's own path, as `preserve` does (`shared.lua` `override_upstream_url`).
